# Ограничения выполненных задач

Решения, которые продолжают ограничивать работу: нарушить их значит сломать
уже работающее. Полных постановок здесь нет — задачи выполнены, и подробности
живут в коде; остались только причины, по которым код именно такой.

Читать перед тем, как «упростить» что-то из перечисленного. Неочевидные
технические решения — в [implementation-notes.md](implementation-notes.md),
что ещё предстоит — в [planning.md](../planning/planning.md).

---

### N-32 (часть Б) · Городской префикс в адресе

`/{locale}/{city}/...` — главная города, каталог и карта. Анкета, кабинет,
вход, админка и страницы «Компания» живут без города.

**Ограничения.**
- **Адрес анкеты без города** — решение владельца продукта. Одна анкета,
  один канонический адрес: город в пути означал бы обязанность вечно
  редиректить прежний адрес при переезде анкеты. Цена — города нет в URL, и
  компенсируется он заголовком, `<h1>` и JSON-LD.
- **Неизвестный город — 404, а не подстановка первого попавшегося.** Чужая
  ссылка не должна молча показать другой город.
- **Город из адреса не переопределяется фильтром.** В каталоге `city`
  берётся из пути после `parseFilters`, иначе
  `/berlin/catalog/escort?city=wien` показал бы чужой город.
- **Старые адреса каталога остались заглушками с 308.** `/{locale}/catalog/…`
  ведёт в первый активный город. 301 переносит вес страницы, 404 его теряет.
  Заодно `catalog` остаётся занятым слугом — иначе город с таким именем
  перекрылся бы этим маршрутом.
- **`/{locale}` сам решает, что показать.** Один активный город — редирект,
  несколько — страница выбора. Поле «город по умолчанию» заводить не
  пришлось, и правило само подстраивается под рост каталога.
- **Переключатель сохраняет страницу**, а не уводит на главную: из каталога
  массажа одного города — в каталог массажа другого. На негородской странице
  и при единственном городе он не отображается вовсе.
- **`CityLink` вместо ручной подстановки.** Язык подставляет обёртка
  next-intl, город — второе измерение; 42 ссылки правились бы вручную и
  однажды разошлись. Без города в адресе `CityLink` отдаёт путь-заглушку,
  та редиректит.
- **`proxy.ts` снимает город перед проверкой доступа по ролям.** Иначе
  правила пришлось бы править при каждом новом городе. Список сегментов,
  которые городом не являются, — тот же `RESERVED_CITY_SLUGS`.

### N-29 · Резервные копии: база и фотографии

**Ограничения.**
- **Сначала база, потом фотографии.** Снимок между дампом и архивом добавит
  файл, на который в базе нет строки, — безвредно. Обратный порядок дал бы
  строку без файла, то есть битую анкету.
- **Шифрование асимметричное, ключ вне сервера.** На машине лежит только
  открытая часть (`backup-public.pem`); закрытая — у владельца. Симметричный
  пароль пришлось бы хранить рядом с копиями, и шифрование защищало бы от
  того, чего не случится.
- **Шифрует хост, а не контейнер `backup`.** В `postgres:17-alpine` нет ни
  openssl, ни age, ни gpg. Ставить их на старте контейнера значит поставить
  бэкапы в зависимость от сети в момент запуска.
- **Открытые файлы на сервере не остаются.** После шифрования исходники
  удаляются: смысл в том, что копия непригодна для чтения и там, где лежит.
- **Проверка разворачивает дамп в отдельную базу.** Проверка, ради которой
  нужно рискнуть рабочей базой, не будет сделана ни разу.
- **Восстановление фотографий останавливает MinIO.** Он держит файлы
  открытыми, и распаковка под работающим контейнером смешала бы старые
  объекты с новыми.

### N-32 · Справочник как зеркало базы

`prisma/reference-data.ts` **генерируется** выгрузкой из базы
(`db:export:reference`) и накатывается обратно сидом. Один файл на страны,
города, районы, услуги и группы — прежние `locations.ts`,
`reference-translations.ts`, `services.ts` и `seed-services.ts` удалены: две
копии справочника однажды разойдутся.

**Ограничения.**
- **Идентификаторы выгружаются и проставляются при создании.** Иначе
  восстановленный на чистой машине справочник получил бы новые id, и всё, что
  на него ссылается, указывало бы в пустоту. Проверено: полный прогон
  «миграции + сид» на пустой базе даёт **те же 83 идентификатора**.
- **Ищем по естественному ключу, id ставим только при создании.**
  `upsert({ where: { slug }, create: { id, ... } })`. Прямой поиск по id
  сломался бы там, где запись уже есть со своим — например на проде, где
  Берлин заведён отдельно от стенда.
- **Порядок записей детерминированный.** Файл лежит в git, и перестановка
  строк от запуска к запуску превращала бы каждый diff в нечитаемый.
  Проверено: повторная выгрузка даёт побайтово тот же файл.
- **Файл исключён из biome** (`!**/prisma/reference-data.ts`). Иначе форматтер
  и генератор спорили бы за формат, и `pnpm lint` падал бы после каждой
  выгрузки. Так же исключён `src/generated`.
- **Отключённые записи выгружаются вместе с остальными.** На них могут
  ссылаться анкеты, и восстановление справочника без них уронило бы внешние
  ключи. У 12 услуг прежних версий каталога переводов нет — выгрузка
  подставляет ключ и предупреждает, а не падает: показать их посетителю
  нельзя, потерять id — можно.
- **Группа без активных услуг в список групп не попадает.** Она не раздел
  интерфейса, а след истории. Сами услуги при этом сохраняются.
- **Правки в админке живут до следующего выпуска.** `make deploy` накатывает
  справочник из файла: отключённый в админке город он включит обратно.
  Порядок работы — поправить в админке, выгрузить, закоммитить.

### N-32 (часть A) · Страны, города и районы из админки

**Ограничения.**
- **Удаления нет нигде, только отключение.** На страну ссылаются города, на
  города и районы — анкеты. Публичные списки фильтруют по `isActive`,
  админские показывают всё.
- **Слуг города не может совпасть с именем маршрута.** `/ru/about` и
  `/ru/berlin` неотличимы по форме, Next разрешает конфликт в пользу
  статического маршрута — город с таким именем молча не откроется.
  `RESERVED_CITY_SLUGS` в `packages/shared/src/locations.ts` сверяется с
  содержимым `apps/web/src/app/[locale]` тестом `reserved-slugs.test.ts`:
  новая страница без обновления списка роняет тест, а не прод.
- **Тест живёт в `apps/api`, а не рядом с константой.** `packages/shared`
  типизирован без node-API намеренно — он ходит и в браузер.
- **Переводы переписываются целиком** (`deleteMany` + `create`), а не
  точечно: частичный набор невозможен по контракту, а точечное обновление
  оставило бы строки от прошлых локалей.
- **Правовое требование кодом не проверяется.** «Страну заводить только после
  урегулирования правовых вопросов» — обязательство владельца, а не инвариант
  системы. Единственная возможная защита — предупреждение в форме, оно есть.
- **Миграция стран написана руками.** `countryId` обязателен, а в `City` уже
  были строки: автоматика такой шаг не выполняет. Порядок в SQL и есть суть —
  сначала страны из существующих кодов, потом связь, потом удаление колонки.

### N-35 · Переводы справочников в БД

Названия городов, районов, услуг и групп хранятся в таблицах переводов;
API отдаёт их уже на языке запроса.

**Ограничения.**
- **Двух копий названий быть не должно.** Ключи `services.*` и
  `serviceGroups.*` из `apps/web/messages/*.json` удалены намеренно.
  Вернуть их «на всякий случай» — значит получить расхождение: справочник
  редактируется из админки, словари фронта — нет.
- **Неполный перевод не сохраняется.** `translatedSchema` в
  `packages/shared/src/locales.ts` требует непустую строку на каждую локаль
  из `LOCALES`. Это решение владельца продукта, а не удобство: запись без
  русского названия показала бы русскоязычному посетителю немецкое слово, и
  он принял бы это за поломку сайта. Схема с необязательными полями такую
  запись пропустила бы.
- **На чтении — падаем на техническое имя, а не на 500.** `localized()`
  в `apps/api/src/i18n.ts` при отсутствии перевода отдаёт `City.name` или
  ключ услуги. Появиться такой записи неоткуда, но ронять весь каталог
  из-за одной строки хуже, чем показать немецкое название.
- **Локаль — параметр запроса, не заголовок `Accept-Language`.** Фронт
  кэширует ответы через ISR по адресу; невидимый в адресе заголовок сложил
  бы три языка в одну запись кэша, и посетитель получал бы чужой.
- **`City.name` и `District.name` остались** как технические имена для
  админки и журналов. Посетителю они не показываются — для этого переводы.
- **Группа услуг — строка в `Service.group`, а не сущность.** Групп семь,
  они не растут; таблица переводов привязана к ключу группы. Названия групп
  тянутся отдельным запросом: связи между `Service` и переводом группы нет.
- **Enum-справочники остаются в коде.** Внешность, тип тела, цвет глаз и
  волос, языки — это `enum` в схеме Prisma, на них завязаны типы, zod-
  контракты и построитель фильтров. Редактируемыми их делать не нужно:
  домен закрытый и не растёт.
- **Демо-сид справочники не заводит.** `db:seed` только читает их и падает
  с подсказкой, если справочник пуст. Заводить города в двух местах значит
  однажды получить разные названия на стенде и на проде.
- **Русские шаблоны с `{city}` падежно-нейтральные.** Город подставляется в
  именительном падеже, и «Анкеты в {city}» давало бы «Анкеты в Берлин».
  Формулировки заменены на «Анкеты — {city}».
- **`scripts/deploy.sh` накатывает справочники каждым выпуском.** Пока
  данные приходят из файлов, это правильно: чистая установка иначе даёт
  пустой каталог. Как только справочники станут редактируемыми из админки
  (N-32, N-36), этот шаг начнёт затирать правки администратора — убрать его
  нужно **там**, а не раньше.

### N-28 · Страницы «Компания»

`/about`, `/advertising`, `/contact` — статические, на трёх языках,
в sitemap с hreflang.

**Ограничения.**
- **Правовых формулировок в текстах нет** — по решению владельца продукта.
  Страницы описывают, что такое проект, сколько стоит размещение и как
  связаться; обязательства, согласия и оговорки живут в правовых страницах
  (L-01) и пишутся юристом.
- **Цены заданы в коде страницы, а не в словарях.** Цена одна на все языки,
  и три копии в трёх файлах однажды разойдутся — в одном останется старая.
- **«О верификации» убрана из футера и из sitemap.** Пока публикуются только
  девушки, проверенные агентством, страница обещала бы собственную процедуру
  проверки, которой нет (L-02).
- **В sitemap только существующие страницы.** Правовые оттуда убраны до
  L-01: ссылка в sitemap, ведущая на 404, хуже её отсутствия.
- **Тарифы — карточками, а не таблицей.** Таблица из трёх колонок на
  телефоне либо жмётся до нечитаемости, либо уезжает прокруткой.

**Поставлено юристу.** Тариф «Агентство» публично противоречит позиции
«само-размещение» (L-07), а цены указаны без пометки о НДС (L-08).

### N-27 · Удаление анкеты и учётной записи

Страница `/account/settings`, запрос удаления с подтверждением паролем,
отсрочка и физическое стирание фоновой задачей `deleted-accounts`.

**Два разных действия.** Удалить одну анкету, не трогая аккаунт (у салона их
до пятидесяти, и убрать одну — обычное дело), и удалить учётную запись
целиком. Раньше существовало только второе, то есть салон, желавший убрать
одну анкету, должен был снести весь аккаунт.

**Ограничения.**
- **Файлы удаляются до строк — это главное здесь.** `Photo` каскадится от
  `Profile`, а тот от `User`: удали пользователя первым, и строки исчезнут,
  а объекты в хранилище останутся навсегда — причём одобренные лежат под
  публичным префиксом. Каскад про файлы ничего не знает, поэтому ключи
  собираются заранее. Проверено: 9 файлов у учётки → 0 после чистки.
- **Удаление файлов живёт в одном месте — `deletePhotoFiles`.** Оба пути
  (анкета и учётка) зовут его, а не удаляют «по-своему»: два способа однажды
  разойдутся, и файл останется в бакете. Список размеров он берёт из
  `VARIANT_WIDTHS`, а не переписывает.
- **«Объекта нет» и «хранилище недоступно» различаются.** Первое
  проглатывается: файла и так нет. Второе пробрасывается и **отменяет
  удаление строк** — иначе ключи потеряны, а файлы остаются в бакете
  навсегда, причём одобренные под публичным префиксом. Лучше не удалить
  сейчас и повторить следующим циклом. Закреплено тестом.
- **Отсрочка, а не мгновенное стирание.** Удаление необратимо, и с угнанной
  сессией без отсрочки стирают чужой заработок, который нечем восстановить.
  Анкеты при этом уходят из каталога **сразу**: обработка прекращается
  немедленно, физическое удаление — вопрос срока
  (`ACCOUNT_DELETION_GRACE_DAYS`, по умолчанию 14 дней).
- **Пароль обязателен для обоих действий**: одного нажатия при угнанной
  сессии быть не должно. У анкеты отсрочки нет — она удаляется сразу, и
  подтверждение остаётся единственной защитой.
- **Сессии намеренно не гасятся.** Отменить удаление можно только войдя,
  и выкидывать человека сразу после запроса значит отнять эту возможность.
- **Отмена не возвращает анкеты в каталог.** Публикация — отдельное решение
  владелицы, а не побочный эффект отмены.
- **Сотрудник не удаляет себя этой кнопкой:** его учётку заводит и убирает
  администратор, самоудаление оставило бы раздел без модератора.
- **Журнал модерации переживает удаление.** Он связан с пользователем
  строковым `subjectId` без внешнего ключа: это записи о решениях
  сотрудников, и стирать их вместе с учёткой значило бы терять
  доказательства. В интерфейсе об этом сказано прямо — умолчать значило бы
  обмануть. Журнал показывает такие строки как «предмет удалён» (N-24).
- **Удаление живёт на отдельной странице настроек**, а не среди анкет
  и избранного, где на него нажимают мимоходом.

### N-26 · Каталог на карте

Кнопка «Анкеты на карте» в шапке рядом с фильтрами, страница
`/catalog/[kind]/map`.

**Ограничения.**
- **Точка — всегда группа, а не одна анкета.** Координаты огрублены до сетки
  (N-14), поэтому анкеты одного района лежат на одинаковых координатах и без
  группировки совпали бы пиксель в пиксель. Кружок с числом честнее булавки:
  показывает плотность и не обещает точности, которой нет.
- **Группировка на сервере.** Число точек ограничено числом ячеек, а не
  числом анкет, — ответ не растёт вместе с каталогом. В карточке точки
  до шести анкет, остальные числом.
- **Отдельный маршрут `/profiles/map`, а не поле в карточке каталога.** Карте
  нужны координаты и минимум подписи, но сразу по всем анкетам; каталогу —
  полные карточки, но постранично. Одна схема на оба случая раздула бы
  листинг ради карты.
- **Фильтры общие с каталогом**: карта читает те же параметры из адреса,
  и переход «список ↔ карта» ничего не сбрасывает.
- **Карта не индексируется** (`noindex, follow`): текста для поиска в ней нет,
  а содержимое дублирует каталог — дубль только отнимает вес у самого
  каталога.
- **Ссылка на карту продублирована в фолбэке `<Suspense>`.** Кнопка живёт
  в клиентском `HeaderFilters` (ей нужны текущие фильтры), а он до гидрации
  показывает фолбэк — без дубля ссылка появлялась бы рывком и отсутствовала
  в серверной разметке.
- **Вид подгоняется под найденное** после смены фильтров: иначе карта
  остаётся на прежнем месте и кажется, что ничего не нашлось.
- Подписи в карточке точки собираются строкой для Leaflet и **экранируются
  вручную** — React в этом месте не участвует.

### N-14 · Карта на странице анкеты

Мозаика статичных плиток 3×2 и круг области поверх неё. Плитки идут через
собственный маршрут `/api/map/{z}/{x}/{y}`.

**Ограничения.**
- **Область, а не точка, и без маркера.** Круг радиусом километр говорит
  «где-то здесь». Булавка читается как точное место, даже когда координата
  приблизительная, — поэтому её нет вовсе.
- **Откуда берутся координаты.** Раньше — ниоткуда: значения задавал
  единственный демо-сид фальшивой формулой, у настоящих анкет их не было
  вовсе, и карта для них не показалась бы никогда. Теперь два источника:
  центр выбранного района (`District.lat/lng`) либо точка, поставленная
  владелицей на карте в кабинете. Ручная точка старше: смена района её
  не сдвигает, сбросить можно кнопкой.
- **Любая координата огрубляется до сетки 0.01° (`snapLocation`, ~1 км)
  на сервере.** Владелица ставит точку сама, но точнее ячейки в базу не
  попадает ничего: внутри ячейки соседние адреса неразличимы. Проверять это
  на клиенте бессмысленно — запрос подделывается. Шаг сетки подобран под
  радиус круга: будь он заметно мельче, точка читалась бы внутри круга.
- **В кабинете показывается круг после огрубления, а не место нажатия.**
  Иначе возникает ложное ощущение, что мы храним точный адрес.
- **У районов нет полигонов.** В `District` только центр — отсюда круг,
  а не контур. Появятся границы, можно заменить: интерфейс не изменится.
- **Leaflet подключён только в кабинете**, за формой входа, динамическим
  импортом. Публичная страница анкеты остаётся без единой библиотеки карт —
  проверено: из 21 скрипта на ней ни один не содержит leaflet.
- **Плитки проксируются через свой домен — это приватность, а не кэш.**
  Обращаясь к чужому тайл-серверу напрямую, браузер сообщает ему адрес
  посетителя, `Referer` со страницей анкеты и то, какой участок он смотрит.
  Для каталога 18+ это по сути «этот человек интересовался этой анкетой»,
  особая категория по ст. 9 GDPR. Адрес поставщика лежит в `MAP_TILE_URL`
  и наружу не публикуется.
- **Маршрут проверяет `z/x/y` сам**, а не полагается на поставщика: без этого
  он превращается в открытый прокси к произвольному пути upstream.
- **Библиотеки карт нет намеренно.** Листать и масштабировать здесь нечего —
  показывается один неизменный участок, — а Leaflet весит около сотни
  килобайт и тянет рантайм на страницу, которая должна оставаться лёгкой
  и попадать в индекс. Плитки грузятся лениво самим браузером.
- **Отношение сторон задано заранее** (`aspect-ratio: 3 / 2`): иначе догрузка
  плиток дёргает разметку — тот самый сдвиг, который портит метрики.
- **Тёмная тема — инверсией плиток**, не отдельным стилем: ярко-белый
  прямоугольник посреди тёмной страницы читается как ошибка.
- **Пустой `MAP_TILE_URL` отключает карту**, остаётся текстовая сноска:
  пустой серый прямоугольник хуже честной строки.

**Решение за владельцем продукта: чей тайл-сервер.** Публичный сервер
OpenStreetMap запрещает такое использование своей Tile Usage Policy —
для прода нужен либо собственный сервер (для одного города достаточно
извлечения Protomaps/OSM), либо коммерческий поставщик с договором,
допускающим проксирование. В `.env.example` значение пустое, локально в
`.env` подставлен OSM только для проверки.

### N-25 · Блокировка: анкеты и учётной записи

**Зачем.** У модератора нет способа что-либо сделать с нарушающей анкетой:
он может закрыть жалобу, но не остановить показ. `ProfileStatus.banned`
объявлен в схеме и не используется нигде. Блокировка учётной записи есть
только у админа и только для сотрудников; причина нигде не хранится, и
заблокированный видит лишь «Учётная запись заблокирована».

**Зависит от:** N-06, N-23 · *(обе выполнены)*

**Два разных действия, и путать их нельзя.**

| | Блокировка анкеты | Блокировка учётной записи |
|---|---|---|
| Что происходит | анкета уходит из каталога | вход перестаёт работать |
| Кто применяет | модератор | модератор |
| Владелица видит | причину в кабинете | причину на форме входа |
| Может исправить | да: правит и отправляет на проверку | нет, только написать в поддержку |
| Когда | нарушение в содержимом | обман, повтор после блокировок |

Требование «владелица видит причину и может отредактировать анкету» выполнимо
**только** для блокировки анкеты: заблокированная учётная запись не может
войти, а значит ни причины не увидит, ни анкеты не поправит. Поэтому основная
мера — блокировка анкеты, а блокировка учётной записи остаётся крайней.

**Ограничения.**
- **Причина обязательна для обеих.** Блокировка без объяснения не оставляет
  человеку способа исправиться и превращает модерацию в произвол.
- **Разблокировка анкеты возвращает её в «приостановлено», а не в
  «опубликовано».** Модератор снимает запрет, но решение показывать анкету
  снова принимает владелица — иначе снятие блокировки молча возвращает в
  каталог содержимое, которое она, возможно, уже сама решила не публиковать.
- **Заблокированная анкета редактируется и отправляется на проверку.** Это
  путь исправления, а не обход: отправка ведёт в очередь, а не сразу в
  каталог.
- **После пройденной верификации кнопки «Отправить на проверку» нет.**
  Отправка переводит заявку обратно в `pending`, то есть уже проверенная
  владелица теряла бы статус и возвращалась в очередь — нажав кнопку, которая
  ей в этот момент не нужна: анкету остаётся только опубликовать. Запрет
  стоит **на сервере** (409), а не только в интерфейсе: это потеря данных,
  и прятать её одним лишь скрытием кнопки нельзя. Единственное исключение —
  заблокированная анкета: там повторная проверка и есть смысл действия,
  а в очередь она попадает именно через сброс заявки в `pending`.
- **Модератор не блокирует сотрудников** — для них есть `/admin/staff`,
  и распоряжаться коллегами не его роль. И не блокирует себя.
- **Блокировка учётной записи гасит все её сессии немедленно**, а не ждёт
  истечения куки.
- **Отдельные списки заблокированных** — учётных записей и анкет, — а не
  фильтры в общем списке и не вкладки очереди. Очередь это то, что ждёт
  решения; здесь решения уже приняты, и смотрят сюда с другой целью:
  вспомнить, за что заблокировали, и при необходимости снять. В списке анкет
  видно причину, владельца и заблокирована ли **ещё и** его учётная запись —
  меры разные, и путать их нельзя.
- **Списки видны и модератору, не только админу.** Блокирует модератор; список,
  в котором он не может найти собственное решение, чтобы его снять,
  бесполезен.
- Обе блокировки пишутся в журнал (N-24) с причиной.

**Что ещё изменилось.** У жалобы в очереди кнопка «Разобрано» переименована
в «Нарушений нет»: прежнее название не говорило, что происходит, а происходит
именно это — жалоба не подтвердилась. Настоящая мера теперь есть отдельно,
в просмотре анкеты, и требует причины. Блокировка анкеты сама закрывает
жалобы на неё.

### N-23 · Жалобы на анкету

Кнопка на странице анкеты, отдельная вкладка в очереди модерации.

**Ограничения.**
- **Вход не требуется** (решение владельца продукта). Заставлять
  регистрироваться того, кто увидел признаки принуждения или
  несовершеннолетнюю, — значит такого сообщения не получить; цена ошибки
  здесь несопоставима с ценой спама. Сдерживание — лимит 10/час на IP и
  `ipHash` в записи, как в N-08. Соотнесение с DSA (ст. 16) — набросок,
  **формулировки перед запуском показать юристу**.
- **Причина — перечисление, пояснение обязательно.** По свободному вводу не
  расставить приоритет и не собрать статистику, а одна категория без
  пояснения непроверяема: «краденые фото» без указания, чьи и где, ничего
  не даёт модератору.
- **`underage` и `coercion` помечены срочными** и идут первыми в очереди,
  отдельным числом в счётчике шапки и красным бейджем в списке. Порядок
  сортировки читается не сразу — цвет виден мгновенно. В форме такая причина
  показывает предупреждение с номером полиции: человек должен понимать,
  что сообщает о возможном преступлении, а не о неудобстве.
- **Жалоба никогда не снимает анкету** (решение владельца продукта). Автоснятие
  по счётчику — готовый инструмент травли конкурентами. У жалобы в очереди
  нет кнопки «одобрить»: разбор её закрывает, а судьбу анкеты модератор
  решает в её просмотре, отдельным действием.
- **Число других открытых жалоб на ту же анкету видно в карточке**: несколько
  независимых сообщений — сигнал сам по себе, но решение всё равно за
  человеком.
- **Заявитель записывается, если входил.** Анонимная жалоба — тоже жалоба,
  и в очереди она помечена как анонимная, а не спрятана.
- Закрытие жалобы пишется в журнал модерации (N-24) как решение по анкете —
  строка кликабельна и ведёт в её просмотр.

### N-24 · Журнал модерации отдельной страницей

`/[locale]/moderation/log`, `noindex`. Предмет решения раскрыт, строка ведёт
в просмотр модератора. Фильтры: сотрудник, тип предмета, решение.

**Ограничения.**
- **Предмет раскрывает сервер.** `subjectId` — это id фото, заявки, отзыва
  или пользователя; собирать из него ссылку на клиенте значило бы зашить туда
  знание о четырёх таблицах. Резолвер делает по одному запросу на тип, а не
  на запись: журнал отдаёт до двухсот строк, и обход в цикле дал бы двести
  запросов.
- **Удалённый предмет не убирает строку.** Фото могло быть вычищено по сроку
  (N-18), учётка — удалена. Строка остаётся с пометкой «предмет удалён»:
  журнал о том, что решение было принято, а не о том, что предмет жив.
  Ссылка при этом не рисуется — мёртвая ссылка хуже её отсутствия.
- **У отзыва показывается учётка автора, а не владелицы анкеты:** решение
  касалось его текста. У фото и заявки — наоборот, владелицы.
- **Модератор видит только свои решения.** Подмена `moderatorId` в запросе
  не помогает: для не-админа фильтр перезаписывается идентификатором из
  сессии. Журнал существует как надзор за сотрудниками, а не как их общая
  лента. Проверено: модератор с чужим id в параметре получает свои четыре
  записи.
- **Журнал только читают.** Ни правки, ни удаления из интерфейса: запись,
  которую можно поправить, перестаёт быть доказательством.
- Все фильтры входят в ключ запроса — иначе ответ на прежний запрос ляжет
  поверх нового при быстром переключении.

### N-22 · Модульная структура фронта

Фича лежит одной папкой: `modules/<фича>/{api.ts, components/}`. `lib/` больше
нет. Слои: `app/` (только маршруты), `layout/`, `modules/`, `design-system/`,
`overlays/`, `shared/`.

**Ограничения.**
- **`app/` содержит только маршруты.** Иначе `page.tsx` перестаёт быть
  надёжным перечнем того, что вообще есть в приложении. Ни `screens`, ни
  `navigation` не заводим: в App Router маршрутизация **есть** дерево файлов,
  и отдельный слой экранов дублировал бы его и разъехался с ним. Эти понятия
  приходят из React Native, где роутер — рантайм, а не файловая система.
- **`query-keys.ts` остался общим** в `shared/`, а не разъехался по модулям.
  Прямое следствие N-19: ключ, собранный не там, где им инвалидируют,
  промахивается мимо кэша молча.
- **Межмодульные импорты — только абсолютные** (`@/design-system/...`),
  относительных `../../` между слоями не осталось: они ломаются при
  следующем переносе и не показывают, к какому слою идёт обращение.
- **Оверлеи сведены к `overlays/Overlay`** — портал в `body`, блокировка
  прокрутки, Escape. Портал здесь суть, а не деталь: предок с `position:
  sticky` создаёт контекст наложения, и `z-index` потомка считается внутри
  него. Полноэкранный просмотр от этого уезжал под шапку, а панель фильтров
  открывается **из** липкой шапки и была заперта ровно так же — эта ошибка
  ещё не проявилась только потому, что выше неё ничего не рисовалось.
- **Гейт 18+ намеренно НЕ переведён на `Overlay`.** Портал монтируется после
  гидрации, а гейт обязан быть в серверной разметке: без JS он иначе не
  покажется вовсе — для каталога 18+ это не косметика. Его блокировка
  прокрутки и скрытие сделаны чистым CSS по `html[data-adult]` и работают
  до и без JS. Он и так лежит корнем в `<body>`, вне чужих контекстов
  наложения, — портал ему нечего исправлять.
- **Шрифты остались в `next/font`.** Папки `assets/fonts` нет: самохостинг
  через `next/font` убирает сдвиг разметки при загрузке, файлы в репозитории
  этого не дают.
- **Стора нет.** По итогам N-19 клиентского состояния, переживающего
  компонент, не осталось; `zustand` удалён из зависимостей.

**Что чуть не сломалось.** Динамический импорт словарей в `i18n/request.ts`
собран шаблонной строкой (`../../messages/${locale}.json`). Типы такое не
проверяют — `tsc` прошёл чисто, а сборка упала: после переезда на уровень
глубже путь стал неверным. Урок на будущее: после переноса файлов зелёный
`typecheck` ничего не доказывает, обязательна сборка.

### N-19 · TanStack Query для клиентских запросов

Клиентские экраны — кабинет, модерация, админка, избранное, отзывы — ходят в
API через Query. Ключи собраны в `lib/query-keys.ts`.

**Ограничения.**
- **Граница с витриной не размывается.** Query отвечает только за запросы из
  браузера. Главная, анкета и каталог по-прежнему грузятся на сервере через
  `lib/api.ts` с ISR: обернуть их в Query значит убить SSG, ради которого
  построен весь фронт. Проверяется выводом `next build`: 21 статическая
  страница, витрина осталась серверной.
- **Ключи только из `queryKeys`.** Ключ, собранный строкой в компоненте,
  однажды разойдётся с тем, по которому лежит кэш, и `invalidateQueries`
  промахнётся. Список после мутации не обновится, ошибка не выпадет —
  экран просто покажет старое, и это спишут на «подвисло».
- **Инвалидация по префиксу там, где ключей несколько.** Решение модератора
  устаревляет и `queue('photo')`, и `queue()` — для этого есть
  `queryPrefixes.queue()`.
- **Клиент создаётся в состоянии, а не в модуле.** Модульная переменная в Next
  живёт дольше запроса и на сервере оказалась бы общей: кэш одного посетителя
  утёк бы другому.
- **Выход чистит кэш целиком** (`queryClient.clear()`), а не только сессию:
  в нём лежат избранное, очередь, анкеты. Порядок важен — сначала `clear()`,
  потом запись `null` в ключ сессии, иначе очистка сотрёт и её.
- **`refetchOnWindowFocus` выключен.** Это экраны за логином; данные меняются
  от действий самого пользователя, и перезапрос при возврате на вкладку
  только мигает интерфейсом.
- **4xx не повторяются.** 401 и 403 — это ответ, а не сбой сети.
- **Локальное состояние осталось там, где оно и есть состояние.** Черновик
  формы анкеты живёт в `useState` и засевается из ответа сервера эффектом:
  пока владелица правит форму, фоновое обновление кэша не должно затирать
  несохранённое. У самого запроса анкеты поэтому `staleTime: Infinity`.
  **Zustand не понадобился и удалён из зависимостей.** Того, что выглядело
  как клиентское состояние, на деле не оказалось: почти всё было серверными
  данными и ушло в Query, а остальное — открытая панель, индекс снимка в
  галерее, черновик формы — живёт в одном компоненте и пробрасывается на
  один уровень. Два места, где состояние действительно общее, — сессия и
  избранное — решены контекстом поверх Query; стор рядом с ним означал бы
  второй кэш и ручную синхронизацию. Вернуть, если появится состояние,
  переживающее компонент: мастер в несколько шагов, корзина, фильтры,
  читаемые одновременно из шапки и из панели.
- **`useQuery` вместо эффекта для подтверждения почты.** Токен одноразовый, и
  двойное монтирование в строгом режиме гасило бы только что подтверждённую
  ссылку; раньше от этого спасал ручной `useRef`-флаг, теперь дедупликация
  идёт из коробки.

### N-20 · Компонент — своя папка

Каждый компонент лежит в своей папке с `index.tsx`. Пути импортов снаружи
не изменились: `@/components/catalog/ProfileCard` как был, так и остался.

**Ограничения.**
- **Общие для раздела стили не разносятся по папкам.** `Account.module.css`
  используют шесть компонентов, `Moderation.module.css` — пять,
  `AuthForm.module.css` — пять. Механический разнос продублировал бы одни и
  те же правила в пяти файлах, а это хуже общего файла. Личный css (15 штук)
  уехал к владельцу, восемь общих остались на уровне раздела.
- **Имя личного css совпадает с именем папки.** Проверено скриптом:
  расхождений нет. `Pagination.module.css` при переносе переименован в
  `CatalogResults.module.css` — он давно принадлежал только ему.
- **Делалось после N-19**, а не до: Query всё равно переписал содержимое этих
  компонентов, и переносить их дважды было незачем.

### N-10 · Комментарии клиентов

Отзывы к анкете от клиентов, с обязательной премодерацией. Жалоба владелицы
и новый отзыв попадают в одну очередь (N-06).

**Ограничения.**
- **Премодерация не опция.** Это высказывания о конкретных живых людях в
  чувствительной сфере: публикация без проверки открывает и диффамацию, и
  травлю, и слив личных данных, а по немецкому праву за размещённое отвечает
  площадка. `status` по умолчанию `pending`, публикация — только решением
  модератора.
- **Числовой оценки нет** (решение 4). Агрегированный рейтинг живого человека
  — автоматическая оценка личности и удобный инструмент травли: несколько
  согласованных единиц топят анкету навсегда. Текст модерируется и снимается,
  среднее арифметическое — нет. Закреплено тестом: в контракте не должно
  появиться ни `rating`, ни `score`, ни `stars`.
- **Публичный список не содержит полей, зависящих от смотрящего.** Он
  отдаётся страницей анкеты и кэшируется ISR; попади туда «можно ли
  пожаловаться» — в кэш лёг бы ответ, посчитанный для случайного гостя.
  Всё личное идёт отдельным запросом из браузера: `comments/mine` для своего
  отзыва, кнопка жалобы — в клиентском компоненте. Тоже закреплено тестом.
- **Опубликованные отзывы рисует сервер.** Это содержимое страницы: оно
  должно попадать в индекс и читаться без JS.
- **Автор видит свой отзыв до публикации** с пометкой «на проверке» и с
  причиной отказа. Без этого кажется, что форма не сработала.
- **Один отзыв на анкету в сутки** — продуктовое правило, а не лимит
  запросов: иначе страница превращается в ленту одного автора. Отдельно от
  этого стоит и обычный лимит, и он не снимается внутренним секретом фронта.
- **Владелица анкеты не отвечает публично** (решение 3), вместо ответа —
  жалоба. Это заметно уменьшает объём модерации и не даёт странице стать
  публичной перепалкой. Обратная сторона: на несправедливый отзыв возразить
  на месте нельзя, поэтому жалобы должны разбираться быстро — иначе
  единственный инструмент защиты не работает. Поэтому же открытая жалоба
  на **опубликованный** отзыв возвращает его в очередь и попадает в счётчик
  в шапке: иначе жалобы копились бы молча.
- **Кнопка жалобы — у любого вошедшего**, не только у владелицы: закрывать её
  ролью значило бы прятать сообщение о нарушении от тех, кто его заметил.
  На собственный отзыв пожаловаться нельзя. Пара «отзыв + заявитель»
  уникальна — повтор даёт 409, а не вторую строку в очереди.
- **Снятие различает `hidden` и `rejected`.** Снаружи разницы нет, но по
  журналу видно, был ли текст когда-то виден людям.
- **Разметки в отзывах нет.** Тело выводится текстом, React экранирует его
  сам; проверено, что `<img onerror>` доезжает до страницы как `&lt;img`.
- **Решение модератора сбрасывает кэш анкеты** по тегу `profile:<slug>` —
  иначе одобренный отзыв всплыл бы через десять минут.

### N-18 · Фоновые задачи по расписанию

Отдельный процесс `jobs`, раз в `JOBS_INTERVAL_SECONDS` прогоняющий чистку
по срокам хранения. Точка входа — `apps/api/src/jobs/runner.ts`, список
задач — `jobs/tasks.ts`.

| Задача | Что удаляет | Умолчание |
|---|---|---|
| `deleted-photos` | мягко удалённые фото и их файлы в хранилище | 30 дней |
| `auth-tokens` | отработавшие токены почты и сброса пароля | 7 дней |
| `contact-reveals` | журнал раскрытий контактов (N-08) | 365 дней |
| `moderation-actions` | журнал решений модерации (N-06) | 365 дней |

**Ограничения.**
- **Отдельный сервис, а не таймер внутри API.** При нескольких репликах `api`
  таймер отработал бы в каждой, а удалять нужно один раз. По той же причине
  отдельным сервисом вынесены миграции.
- **Замок в Redis поверх этого.** Задачи идемпотентны, но два процесса,
  одновременно перебирающие фотографии и удаляющие объекты из хранилища,
  мешают друг другу и шумят ошибками «объект не найден». TTL замка заведомо
  больше цикла: умерший процесс задержит следующий запуск не дольше него.
  Замок снимается сразу после цикла, а не по TTL, — иначе следующий заход
  упёрся бы в собственный незакрытый замок.
- **Сроки — в конфигурации, а не в коде.** Это обязательства перед
  регулятором: менять их приходится по юридическому решению, и требовать
  ради этого выката новой версии неправильно.
- **Ошибка одной задачи не отменяет остальные.** Чистка фотографий зависит от
  хранилища, чистка журналов — только от БД; недоступный MinIO не должен
  означать, что журналы копятся дальше. Проверено тестом.
- **Ноль тоже пишется в лог.** Молчаливая чистка неотличима от незапущенной,
  и на вопрос «почему база растёт» тогда некуда посмотреть.
- **Живой неиспользованный токен не трогается.** Условие только по
  `expiresAt`/`usedAt`, а не по `createdAt`: иначе ссылка из письма
  переставала бы работать раньше собственного срока. Проверено тестом.
- **Чистки документов верификации в списке нет.** Приёма документов ещё не
  существует (см. L-02 в `legal.md`), а задача, удаляющая несуществующее,
  создаёт ложное чувство исполненного обязательства. Вернуть вместе с L-02.

### N-09 · Избранное

Сердце на карточке и на странице анкеты, страница `/account/favorites`.

**Ограничения.**
- **Составной первичный ключ `@@id([clientId, profileId])`** — он же защита от
  дублей. `PUT` идемпотентен через `upsert`, `DELETE` через `deleteMany`:
  повторное нажатие не создаёт вторую строку и не падает конфликтом, и
  предварительная проверка «а есть ли уже» не нужна — она была бы гонкой.
- **Только роль `client`.** Не «есть сессия»: иначе владелица анкеты собирала
  бы себе список конкуренток. Рекламодателю и персоналу API отвечает 403,
  а сердце им не показывается вовсе — кнопка, которая всегда не работает,
  хуже её отсутствия.
- **Отметить можно только опубликованную анкету.** Иначе `PUT` по прямому id
  стал бы способом узнать, что черновик существует.
- **Снятая с публикации анкета остаётся в избранном** с пометкой и перестаёт
  быть ссылкой — вести на 404 хуже, чем показать, что анкеты больше нет.
  Сердце при этом продолжает работать: иначе отметку было бы не снять.
  Ради этого у `ProfileCard` появился проп `unavailable`, а не CSS-приглушение
  снаружи — `pointer-events: none` убил бы вместе со ссылкой и кнопку.
- **Один запрос на страницу, а не по одному на карточку.** `FavoritesProvider`
  тянет `GET /me/favorites/ids` один раз при известной роли; карточки читают
  из общего множества. Отдельный лёгкий маршрут потому, что ради подсветки
  двух десятков сердец тянуть двадцать полных карточек незачем.
- **Нажатие гостя не теряется.** Идентификатор кладётся в `sessionStorage`,
  человек уходит на вход и возвращается с уже поставленной отметкой.
  `sessionStorage`, а не `localStorage`: намерение живёт до конца вкладки,
  иначе забытое сердце всплыло бы через неделю.
- **Переключение оптимистично**, откат при отказе. Сердце должно откликаться
  мгновенно — сеть тут ни при чём.
- **Страница избранного — `noindex, nofollow`** и вне sitemap: это личный
  список, и в выдаче он был бы ссылкой на чужой экран входа.
- **SSG сохранён.** Страница остаётся статической оболочкой, данные приходят
  запросом из браузера: чтение сессии на сервере убило бы пререндер.
- **Вошедшего на формы входа и регистрации не пускаем.** Проверка по сессии,
  а не по куке-подсказке: кука переживает отозванную сессию, и по ней
  забаненный не смог бы дойти до формы, чтобы войти заново. Возврат идёт на
  `?next=`, но только если это относительный путь: `//evil.com` и
  `/\evil.com` браузер читает как чужой домен, поэтому проверки на ведущий
  `/` недостаточно. Формы обёрнуты в `<Suspense>` — `useSearchParams` без
  границы уводит страницу целиком в клиентский рендер.

### N-08 · Контакты анкеты с гейтом показа

Телефон, WhatsApp, Telegram и Viber. До нажатия — заглушённые строки,
после — кликабельные ссылки.

**Ограничения.**
- **Контактов нет в разметке — это суть задачи, а не деталь.** Отдай их SSR-HTML
  и спрячь через CSS, и гейт станет декоративным: вся база собирается одним
  `curl`. Публичное представление анкеты отдаёт только `contactTypes` —
  какие способы связи есть, без значений. Значения приходят единственным
  маршрутом `POST /profiles/:slug/contacts/reveal` в ответ на явное действие.
  Поэтому же блок контактов — клиентский компонент: серверный вписал бы
  значения и в HTML, и в RSC-payload.
- **Нормализация обязательна и живёт на сервере.** «0170 123 45 67» и
  «+49 170 1234567» — один номер; сохрани их как набраны, и в базе окажутся
  две строки, а `@@unique([profileId, type, value])` этого не заметит.
  Телефон приводится к «плюс и цифры», Telegram — к `@нику`. Вставленный
  национальный номер с ведущим нулём и запись через `00` распознаются.
- **Ни формат, ни длина номера не проверяются** — решение владельца продукта.
  Поле ввода гарантирует ведущий «+» маской (`maskContactValue`) и не пускает
  в номер буквы; единственный отказ на сервере — цифр нет вовсе, сохранять
  нечего. Верхнюю границу задаёт схема хранения (64 знака), а не
  представление о «правильной» длине. Прежние правила — «код страны
  обязателен», «от 8 до 15 цифр» — ловили владелицу на ошибке там, где
  ошибки не было: настоящую проверку номера без справочника планов
  нумерации всё равно не сделать, а её имитация отвергает живые номера.
- **Маска лежит рядом с нормализацией, в `packages/shared`.** Разъедься они
  — форма разрешит набрать то, что сервер потом отвергнет.
- **Ник вместо номера принимает только Telegram.** `wa.me/<цифры>` и
  `viber://chat?number=` строятся исключительно по номеру, ника в них нет.
  Разрешить ник в этих каналах значит показать посетителю ссылку, которая
  никуда не ведёт.
- **Вход для раскрытия не требуется** (решение 2). Сдерживание сбора — лимит
  20/час на IP и журнал раскрытий, больше ничего. Плата принята осознанно:
  статистика откликов считает обращения, а не людей.
- `ipHash` — соль плюс SHA-256, не сырой адрес: журнал не должен сам стать
  базой персональных данных. Соль постоянная, иначе записи одного человека
  перестанут схлопываться; из-за этого хэш обратим перебором адресов —
  поэтому строки живут 365 дней (`purgeContactReveals`), а не вечно.
- Контакты неопубликованной анкеты отдают 404, как и сама анкета: раскрытие
  не должно быть обходным путём к скрытому черновику.
- Дубли после нормализации схлопываются молча, а не падают ошибкой: приводили
  к одному виду мы, наказывать за это владелицу не за что.
- **Лимит раскрытия не освобождается ничем** — ни внутренним секретом фронта,
  ни доверенным прокси. Он про приватность владелицы, а не про пропускную
  способность; подробности и история — в `documentation/arch/implementation-notes.md`.

### N-01 · Возрастной гейт 18+

Оверлей поверх контента, подтверждение в куке `noova_adult` на год.

**Ограничение.** Куку нельзя читать на сервере: `cookies()` в layout переводит
приложение в динамический рендер и убивает SSG. Атрибут на `<html>` ставит
инлайн-скрипт в `<head>`, оверлей скрывает CSS. Разметка каталога остаётся
в DOM — боты видят контент.

### N-02 · Аккаунты: регистрация, вход, роли

Роли `client` / `advertiser` / `moderator` / `admin`. Регистрация только по
email; у клиента обязателен один никнейм. У рекламодателя есть
`advertiserKind`: `individual` — одна анкета `escort`, `salon` — много
`massage`. Смешивать нельзя, это правовое ограничение из §0.

**Ограничения, которые нельзя нарушать.**
- Пароли — argon2id (`@node-rs/argon2`, есть бинарники под musl).
- Сессии серверные, в Redis: учётку нужно уметь мгновенно отзывать при бане,
  а выданный JWT отозвать нельзя. Идентификатор сессии меняется при каждом входе.
- **Никакого перечисления пользователей.** Регистрация на занятый email и
  сброс пароля на несуществующий адрес отвечают ровно как при успехе. Форма
  не должна работать оракулом «есть ли у вас тут аккаунт».
- `AuthToken` хранит только SHA-256 токена: утечка таблицы не даёт рабочих ссылок.
- Смена пароля гасит все сессии.

Год рождения хранится вместо возраста — возраст протухает.

### N-16 · Состояние сессии на фронте

Шапка показывает меню пользователя, не ломая статику.

**Ограничение.** Сессию нельзя читать на сервере по той же причине, что и
возрастной гейт. Схема: API ставит вторую куку `noova_signed_in` (без секрета,
доступную JS), инлайн-скрипт проставляет `data-signed-in` на `<html>`, шапка
держит в разметке оба блока, CSS показывает нужный. Данные пользователя
подтягивает `SessionProvider` после гидратации.

### N-17 · Сброс кэша по событию

`POST /api/revalidate` во фронте, вызов `fastify.revalidate(tags)` из API.

**Ограничение для будущих задач.** Любой маршрут, меняющий публичные данные,
обязан сбрасывать кэш, иначе правка не видна до 10 минут. Теги:
`profile:<slug>` и `profiles`. Вызов не блокирующий — недоступность фронта
не должна ронять сохранение. В разработке кэш API-ответов отключён вовсе.

### N-04 · Кабинет владельца

Создание и редактирование анкет, тарифы, услуги из справочника, отправка на
проверку, публикация и снятие с публикации.

**Ограничения.**
- Владение проверяется на каждом запросе; чужая анкета отдаёт **404, а не 403** —
  иначе перебором выясняется, какие id существуют.
- Вид анкеты следует из `advertiserKind` владельца и из запроса не берётся.
- **Slug неизменяем.** Генерируется один раз из имени и города, смена имени
  его не трогает. Это снимает нужду в 301 и бережёт внешние ссылки.
- Публикация запрещена без `VerificationCase.status = verified`, проверка на сервере.
- `fromPriceCents` денормализован — пересчитывается при каждой правке тарифов.

Справочник услуг — в `apps/api/prisma/services.ts`, наполняется идемпотентным
`db:seed:services`. Свободные теги отменены: написанные руками, они расходятся
в формулировках, не переводятся и не годятся для фильтров. Услуга, выпавшая из
каталога, деактивируется, а не удаляется — удаление порвало бы связи с анкетами.

### N-06 · Модераторская очередь

Раздел `/moderation` для ролей `moderator` и `admin`, `/admin` — только для
`admin`. Очередь показывает фотографии, заявки на верификацию и список
пользователей; решения пишутся в `ModerationAction`.

**Ограничения.**
- Роль проверяется на сервере хуком `requireRole`, а не прячется в интерфейсе.
- **Модератор не модерирует своё** — проверка по `ownerId`, даже при том что
  роли разведены по разным учётным записям.
- Зарегистрироваться модератором снаружи нельзя: регистрация принимает только
  `client` и `advertiser`. Сотрудников заводит `admin` в `/admin`, первого
  администратора — разовый скрипт `db:create-admin`.
- Отказ требует причину не короче 5 символов: её видит владелец анкеты,
  и без неё он не поймёт, что исправлять.
- Блокировка сотрудника гасит его сессии немедленно. Себя заблокировать нельзя.
- Фото в очереди отдаются по подписанным ссылкам — непроверенный снимок
  не становится публичным оттого, что его смотрит модератор.
- **Ручное подтверждение почты** (вкладка «Пользователи») обходит
  доказательство владения адресом: сотрудник ручается вместо письма. Поэтому
  оно обязательно пишется в журнал с типом `user` — иначе не выяснить, кто
  и за кого поручился. Временная мера до N-15; когда почта заработает,
  подтверждать вручную должно стать исключением, а не нормой.

### Доступ по ролям (без номера — делалось по ходу)

Витрина закрыта для тех, кому она не нужна: сотрудников уводит на
`/moderation`, владельцев анкет — на `/account/profiles`. Вторая строка шапки
вместо фильтров показывает быстрые ссылки по роли, а блок «Анкеты рядом»
на странице анкеты скрыт от всех, кроме клиента и гостя.

**Ограничения.**
- Редиректы построены на куке `noova_role`. Она **не разграничивает доступ**:
  подделывается тривиально и влияет только на то, какую страницу открыть.
  Все разрешения проверяются на сервере по сессии в Redis.
- Владельцу анкеты `/profile/*` оставлен — иначе он не увидит собственную
  анкету глазами посетителя. Каталога у него нет, так что просматривать чужие
  массово всё равно неоткуда.
- Скрытие «Анкет рядом» сделано CSS по атрибуту документа, а не условием
  в компоненте: страница статическая, роль на сервере не прочитать, а условный
  рендер на клиенте дал бы вспышку.
- Гость и бот не задеты — им витрина доступна целиком.

### N-15 · Отправка почты

SMTP через nodemailer, письма на трёх языках, очередь в Redis.

**Ограничения.**
- **Собственный Postfix, не массовый ESP.** Крупные сервисы ограничивают adult
  в ToS, и блокировка аккаунта остановила бы регистрацию и сброс пароля —
  то есть вход на сайт. Плата: PTR-запись, прогрев IP, присмотр за чёрными
  списками, SPF/DKIM/DMARC. Без PTR письма отклоняются на входе.
- **Отправка не внутри HTTP-запроса.** Письмо кладётся в очередь Redis, шлёт
  фоновый цикл с экспоненциальными повторами. Недоступность SMTP не должна
  превращаться в 500 на регистрации.
- **`BRPOP` на отдельном подключении** к Redis: он блокирует клиент, и на общем
  соединении встали бы сессии.
- **Ни тела письма, ни токена в логах.** Раньше `LogMailer` печатал ссылку
  целиком, и журналы были связкой ключей от всех учётных записей. Поля
  добавлены в `redact`.
- Язык письма берётся из `User.locale` (проставляется при регистрации из
  `accept-language`). Уведомление о попытке регистрации на занятый адрес идёт
  на языке **владельца** адреса, а не того, кто заполнял форму.
- Локально письма принимает Mailpit (`docker-compose.dev.yml`,
  http://localhost:8025) — путь письма проверяется целиком, а не по логу.

**Осталось при развёртывании.** PTR, SPF, DKIM, DMARC и прогрев адреса —
инфраструктурные шаги, которые нельзя сделать из кода. Обработка bounce-ов
не реализована.

### Каталог услуг и параметры анкеты — состав от владельца продукта

Справочник наполнен: 61 услуга в семи группах — сопровождение, секс, массаж,
стриптиз, экстрим, садо-мазо, формат встречи. Порядок групп в файле определяет
порядок в интерфейсе и фильтрах.

**Разделение, которое стоит держать.** Телосложение, тип груди, интимная
стрижка, пирсинг и татуировки — это **параметры анкеты**, а не услуги: они
описывают человека, а не то, что он делает. Поэтому они поля `Profile`
(перечисления и флаги), показываются в секции «Внешность» и не попадают в
раздел «Услуги». Смешивать их со справочником было бы быстрее, но на странице
анкеты «Татуировки» оказались бы среди оказываемых услуг.

**Порядок секций задан продуктом:** внешность → цены → сопровождение → секс →
остальное. Он же в форме редактирования, он же будет в панели фильтров.

**Снятая услуга не удаляется, а деактивируется** — связи с анкетами
сохраняются. У этого два следствия, и оба пришлось закрывать отдельно.

*На отображении.* В анкете встречается ключ, которого нет в словаре, и `t()`
на нём падает, унося всю страницу. Перевод берётся с запасным вариантом —
показывается сам ключ. Некрасиво, но несравнимо лучше белого экрана.

*На сохранении.* Проверка ключей отклоняла снятую услугу, и владелец не мог
сохранить собственную анкету из-за изменения справочника, которое сделал не он.
Теперь принимается ключ, который **либо активен, либо уже привязан к этой
анкете**; выдуманный и снятый-но-чужой по-прежнему дают 400 с указанием ключа.
Форма при этом показывает только активные услуги: оставлять в состоянии то,
чего владелец не видит, значит заставлять его сохранять вслепую.

### N-13 · Пагинация каталога

Один элемент управления, две пагинации под ним.

**«Показать ещё» — это ссылка.** Не кнопка со скриптом, а `<a href="?page=2"
rel="next">`, которую JS перехватывает и обрабатывает у себя. Человек остаётся
на месте и получает следующую порцию в ту же сетку; бот, который на клик не
способен, идёт по адресу и обходит каталог до конца. Клик с Cmd/Ctrl/Shift и
средней кнопкой не перехватывается — «открыть в новой вкладке» продолжает
работать. Отдельного ряда «предыдущая/следующая» нет: он дублировал бы для
человека то, что уже делает кнопка.

**Курсор для человека, смещение для бота.** Подгрузка идёт по курсору, а не по
номеру страницы: при добавлении анкеты смещение съезжает, и человек увидел бы
карточку дважды или пропустил её. Курсор от этого не страдает. Боту курсор не
нужен — ему нужен постоянный адрес, поэтому в `href` стоит `page`.

**Сетка одна.** Отрисованное сервером и догруженное лежат в одном контейнере:
два контейнера дали бы шов и разъехавшиеся ряды. Список живёт в состоянии,
сервер задаёт начальное значение — бот всё равно получает первые карточки
в HTML.

**Ограничения.**
- `canonical` со всех страниц указывает на базовый срез: страницы выдачи —
  один раздел, а не разные документы.
- Ссылка сохраняет текущие фильтры и считает номер следующей страницы от
  числа уже показанных карточек, а не от исходного `page`, — иначе после двух
  подгрузок она вела бы назад.
- Подгрузка отбрасывает уже показанные id: повторное нажатие или гонка
  не должны множить карточки.
- Смещение и курсор взаимоисключающи в одном запросе.

### N-12 · Фильтры по категориям

Панель фильтров и страница каталога `/catalog/[kind]`. Порядок групп задан
продуктом: внешность → цена → услуги по группам → языки → доступность.

**Ограничения.**
- **Порядок групп: цена → внешность → услуги → языки → доступность.** Цена
  первой потому, что по ней отсеивают в первую очередь, и держать её за
  списком параметров внешности значит прятать главное.
- **Список языков — один на фильтр и на форму редактирования**
  (`SPOKEN_LANGUAGES` в `packages/shared`). Разойдись они — владелица укажет
  язык, по которому её никто не найдёт, либо наоборот. Ровно это и было:
  фильтр по языкам существовал, а поля в редакторе анкеты не было вовсе.
- **«С отзывами» считает только опубликованные** (`status: 'published'`):
  анкета со снятым по жалобе комментарием в этот срез не попадает.
- **Состояние живёт в URL, а не в React.** Иначе выдачу нельзя переслать
  ссылкой, кнопка «назад» ведёт себя неожиданно, а сервер не знает, что
  рендерить. Промежуточного «черновика» фильтров нет: правка применяется сразу.
- Запись идёт через `replace`, а не `push` — иначе история распухает от
  каждого нажатого чипа и кнопка «назад» перестаёт работать осмысленно.
- Смена любого фильтра сбрасывает страницу на первую: иначе человек остаётся
  на пятой странице выдачи, в которой теперь две позиции.
- **Индексируется только базовый срез.** Комбинации фильтров дают тысячи
  почти одинаковых URL; при любом применённом фильтре страница отдаёт
  `noindex, follow`, canonical всегда указывает на базовый адрес.
- Мусор в query не роняет страницу: при неудачном разборе показывается
  каталог без фильтров, а не ошибка.
- Страница динамическая (`ƒ`) — это осознанно: кэшировать выдачу с
  произвольными параметрами нечем, а серверный рендер боты всё равно получают.

**Пагинация** — в N-13.

### N-11 · Параметры внешности

Цвет волос и глаз, размер груди, тип внешности — перечислениями, не строками.
Фильтры каталога расширены этими полями и языками.

**Ограничения.**
- **Тип внешности, а не раса.** Данные о расовом или этническом происхождении —
  особая категория по ст. 9 GDPR. `appearanceType` описывает облик,
  заполняется самим владельцем и остаётся необязательным. Слов «раса» и
  «национальность» нет ни в одном из трёх словарей — проверено скриптом.
- **Поле `nationality` убрано из API и интерфейса.** Оно осталось с первой
  версии и было тем самым происхождением, только свободной строкой — хуже,
  чем enum. Колонка помечена в схеме к удалению отдельной миграцией.
- **Enum, а не строка.** По свободному вводу фильтр не собрать: «blonde»,
  «Blond» и «блондинка» окажутся разными значениями, и перевести их нельзя.
  В БД лежит ключ, подпись приходит из словаря.
- Миграция **преобразует** прежние строки в enum, а не сносит колонку:
  сгенерированный Prisma вариант с `DROP COLUMN` потерял бы данные на стенде,
  где они есть. Неопознанные значения становятся NULL.
- У салонов секции внешности нет: поля nullable, форма их не показывает.
- Внутри одного фильтра значения складываются через ИЛИ, между фильтрами —
  через И: «голубые или зелёные глаза» это выбор из списка, а не пересечение.

### N-05 · Фотографии

Загрузка, три размера, порядок, мягкое удаление, полноэкранный просмотр.

**Ограничения.**
- **EXIF снимается на сервере.** Снимок с телефона несёт GPS-координаты, то есть
  домашний адрес — ровно то, что продукт защищает огрублением координат до района.
- Формат определяется по содержимому через sharp: расширение и `Content-Type`
  задаёт клиент.
- **Доступ разделён префиксами, а не флагом.** Бакет отдаёт анонимно только
  `public/*`; неодобренное фото лежит в `pending/*` и недоступно по прямой
  ссылке. Владелец видит его по подписанной ссылке на 10 минут. Одобрение —
  это перенос объектов, и только потом смена флага.
- Минимального разрешения нет; от «бомб сжатия» защищает лимит sharp на
  входные пиксели.
- Удаление мягкое: ошибка владельца обратима, стирание из хранилища — нет.
