# Выпуск

Как заполнить `.env` и как выкатывать код. Выпуск — одна команда:

```bash
make deploy SERVER=deploy@<IP>
```

Перед первым выпуском машина должна быть готова — [server.md](server.md).

---

## 1. `.env`

### Файлов два, и это не один и тот же файл

Путаница здесь стоит дороже всего, поэтому по порядку.

| Файл | Где лежит | Что в нём |
|---|---|---|
| `.env` | ваша машина | разработка: localhost, `pnpm dev`. Для выпуска не используется |
| `.env.deploy` | ваша машина | **две** строки: продовые `SITE_URL` и `PUBLIC_API_URL` |
| `.env` | сервер, `~/noova/` | вся продовая конфигурация и секреты |

Секреты на сервер не копируются ниоткуда — они там и рождаются. `make deploy`
этот файл не создаёт и не перезаписывает; он меняет в нём только `IMAGE_TAG`
и `IMAGE_PREFIX`.

**Локально, `.env.deploy`** — больше от вас ничего не требуется:

```bash
cat > .env.deploy <<'EOF'
SITE_URL=https://noova.cc
PUBLIC_API_URL=https://noova.cc
EOF
```

Только эти две переменные запекаются в браузерный бандл на сборке, поэтому
только они и нужны на вашей машине. Остальное compose подставит на сервере.

> При сборке compose предупредит про непустой список неустановленных
> переменных — `MINIO_ROOT_USER`, `SITE_DOMAIN` и прочие. Это ожидаемо:
> сборке образов они не нужны, читаются они уже на сервере.

**На сервере, `~/noova/.env`.** Одной командой:

```bash
make server-env SERVER=deploy@<IP> DOMAIN=noova.cc EMAIL=admin@example.com
```

Секреты генерируются на сервере и никуда не уезжают. Существующий файл
скрипт **не перезаписывает**: перезапись сменила бы `POSTGRES_PASSWORD`, и
база осталась бы недоступна вместе со всеми данными.

> Сделайте копию `.env` вне сервера. Без `POSTGRES_PASSWORD` дамп базы
> восстановить нельзя — и бэкапы окажутся бесполезны ровно тогда, когда
> понадобятся.

То же вручную, если нужно разобрать по шагам:

```bash
ssh deploy@<IP>
mkdir -p ~/noova && cd ~/noova
DOMAIN=noova.cc          # ваш домен
EMAIL=admin@example.com  # для писем Let's Encrypt

cat > .env <<EOF
SITE_DOMAIN=$DOMAIN
SITE_URL=https://$DOMAIN
PUBLIC_API_URL=https://$DOMAIN
MEDIA_BASE_URL=https://$DOMAIN/media
ACME_EMAIL=$EMAIL

POSTGRES_USER=noova
POSTGRES_DB=noova
POSTGRES_PASSWORD=$(openssl rand -base64 32 | tr -d '/+=')
MINIO_ROOT_USER=noova-minio
MINIO_ROOT_PASSWORD=$(openssl rand -base64 32 | tr -d '/+=')

IP_HASH_SALT=$(openssl rand -hex 32)
INTERNAL_API_TOKEN=$(openssl rand -hex 32)
REVALIDATE_SECRET=$(openssl rand -hex 32)

MAIL_DOMAIN=$DOMAIN
MAIL_FROM="Noova <noreply@$DOMAIN>"

IMAGE_PREFIX=noova
IMAGE_TAG=latest
EOF
chmod 600 .env
```

`tr -d '/+='` не косметика: пароль Postgres уходит в строку подключения
`postgresql://user:пароль@postgres:5432/...`, и слэш с плюсом её ломают.

Значения по умолчанию (`LOG_LEVEL`, `RETENTION_*`, `BACKUP_*`,
`JOBS_INTERVAL_SECONDS`, `S3_BUCKET`, `S3_REGION`) заданы прямо в
`docker-compose.yml` — в `.env` их писать незачем, пока не понадобится
поменять.

### Что читается на сервере

Файл общий для локальной разработки и сервера, но переменные разные.
**На сервере обязательны эти** — у них нет значения по умолчанию, и пустыми
они ломают стек:

| Переменная | Что ставить |
|---|---|
| `SITE_DOMAIN` | `noova.cc` — без схемы |
| `SITE_URL` | `https://noova.cc` |
| `PUBLIC_API_URL` | `https://noova.cc` — API на том же домене |
| `MEDIA_BASE_URL` | `https://noova.cc/media` |
| `ACME_EMAIL` | ваш адрес — туда придут письма об истечении сертификата |
| `POSTGRES_USER` | `noova` |
| `POSTGRES_DB` | `noova` |
| `POSTGRES_PASSWORD` | `openssl rand -base64 32`, без `/`, `+`, `=` |
| `MINIO_ROOT_USER` | любое имя, не `noova` |
| `MINIO_ROOT_PASSWORD` | `openssl rand -base64 32` |
| `IP_HASH_SALT` | `openssl rand -hex 32` |
| `REVALIDATE_SECRET` | `openssl rand -hex 32` |
| `INTERNAL_API_TOKEN` | `openssl rand -hex 32` |
| `MAIL_DOMAIN` | `noova.cc` |
| `MAIL_FROM` | `"Noova <noreply@noova.cc>"` |

**Три секрета обязаны быть случайными.** Оставить значения из примера —
значит: по `IP_HASH_SALT` восстанавливаются адреса из журналов перебором;
по `INTERNAL_API_TOKEN` любой снимает себе лимит запросов; по
`REVALIDATE_SECRET` любой сбрасывает кэш сайта в цикле.

**Что на сервере не используется** (нужно только для локального запуска
вне контейнеров): `DATABASE_URL`, `REDIS_URL`, `S3_ENDPOINT`,
`S3_ACCESS_KEY`, `S3_SECRET_KEY`, `SMTP_HOST`, `SMTP_PORT`,
`WEB_REVALIDATE_URL`. В контейнерах эти значения задаёт
`docker-compose.yml`, и правки в `.env` на них не влияют — доступ к
хранилищу api и jobs получают по `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`.

**Выводятся из других переменных, задавать не нужно:** `CORS_ORIGINS`,
`NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_API_URL` и `NEXT_PUBLIC_MEDIA_URL`
compose берёт из `SITE_URL` и `PUBLIC_API_URL`. Строка в `.env` на сервере
на них не влияет — она просто не читается.

> `NEXT_PUBLIC_MEDIA_URL` — единственная из них, что нужна **на сборке**, а
> не в рантайме: `next.config.ts` строит из неё `images.remotePatterns`.
> Если она не доедет до сборки, оптимизатор картинок ответит
> `"url" parameter is not allowed` на каждую фотографию с боевого домена, и
> лечится это только пересборкой. Поэтому compose подставляет туда `SITE_URL`,
> а не одноимённую переменную: в локальном `.env` она стоит в `localhost:9000`
> и молча испортила бы прод-сборку.

`S3_BUCKET` и `S3_REGION` на сервере читаются, но имеют разумные значения
по умолчанию (`noova-media`, `us-east-1`) — трогать их незачем.

**Необязательные:** `MAP_TILE_URL` (пусто — карты выключены, остаётся
текстовая сноска), сроки хранения `RETENTION_*`, `JOBS_INTERVAL_SECONDS`,
`BACKUP_*`, `RATE_LIMIT_*` — у всех разумные значения по умолчанию.

## 2. `make deploy`

Собирает у вас, привозит на сервер, запускает и проверяет. Ни git, ни
исходников, ни учётной записи GitHub на сервере не требуется: туда едут
готовые образы и три файла — `docker-compose.yml`, `Caddyfile` и скрипты
бэкапа.

```bash
make deploy SERVER=deploy@<IP>
```

На сервере
```bash
docker compose up -d --no-build
```



Внутри — `scripts/deploy.sh`. Он делает то же, что делали бы руками, плюс
четыре вещи, которые руками забываются:

1. **Тег по коммиту.** `IMAGE_TAG` берётся из `git rev-parse --short HEAD`;
   грязное дерево помечается суффиксом `-dirty`, чтобы такой образ потом не
   приняли за содержимое коммита.
2. **Проверки до сборки.** Пустой или localhost-адрес в `SITE_URL` ронял бы
   выпуск уже на сервере — а лечится он только пересборкой. Заодно
   проверяется доступ по ssh и наличие `.env` на сервере.
3. **Дамп базы перед миграциями.** `prisma migrate deploy` необратим, дамп —
   единственный способ вернуться. Пропускается на первом выпуске, когда
   контейнера `backup` ещё нет.
4. **Ожидание healthcheck и запрос снаружи.** Без этого команда завершается
   успехом на стеке, который в этот момент уходит в рестарт-цикл.

### Платформа: Apple Silicon против x86-сервера

Docker собирает под платформу той машины, где идёт сборка, и делает это
молча. Образ, собранный на Mac с arm64, на обычном x86-сервере не
запустится — контейнеры падают с `exec format error`, причём сборка и
перенос до этого проходят «успешно».

Скрипт спрашивает у сервера `uname -m`, выставляет `DOCKER_DEFAULT_PLATFORM`
под него и после сборки проверяет, что образ действительно той архитектуры.

Плата за это — скорость: сборка под чужую платформу идёт через эмуляцию и
занимает десятки минут вместо пары. Если это станет мешать, вариантов два —
собирать в CI (раннеры amd64, эмуляции нет) или прямо на сервере.

### Шум в логе сборки — это норма

`next build` пререндерит страницы, а API в этот момент нет, и в лог валится
`ECONNREFUSED` по разу на каждую из 47 страниц:

```
[api] headerCatalog недоступен, отдаём запасное значение TypeError: fetch failed
```

Так и задумано — см. `safely()` в `apps/web/src/shared/api.ts`. Страницы
собираются с запасными значениями, а ISR подтягивает данные на первом же
цикле: главная — `revalidate = 300`, анкета — `600`. Плюс `api` дёргает
`WEB_REVALIDATE_URL` при изменениях, так что каталог наполняется раньше.

На что смотреть в этом логе: строки `ERROR` и `error:` от самого buildx.
Сообщения `[api] … недоступен` игнорируйте.

### Что происходит на сервере

Порядок запуска стек держит сам:

1. Поднимаются Postgres, Redis, MinIO — с проверками готовности.
2. `migrate` накатывает миграции; отдельным контейнером, потому что при
   нескольких репликах `api` они подрались бы за блокировку.
3. `minio-init` создаёт бакет и открывает анонимное чтение **только**
   префикса `public/`. Непроверенные фотографии лежат в `pending/` и
   остаются недоступными по прямой ссылке.
4. `api` стартует после обоих, `web` — после healthcheck `api`.
5. `caddy` выпускает сертификат и проксирует: `/api/*` и `/healthz` в `api`,
   `/media/*` в MinIO, остальное в `web`.

Наружу смотрит только Caddy — остальные сервисы портов не публикуют.

**Миграции применяются сами.** Контейнер `migrate` отрабатывает до старта
`api` и завершается; `prisma migrate deploy` идемпотентен, повторный запуск
на той же базе ничего не делает. Compose поднимает его заново при каждом
выпуске, дожидается завершения и только потом пересоздаёт `api` — разнести
это руками значит получить новый код на старой схеме.

### Про тег образа

`IMAGE_TAG` лучше ставить по коммиту, а не `latest`. Тогда откат — это
смена одной строки в `.env` и `docker compose up -d`, а не выяснение,
какой образ там был вчера. `latest` не даёт ответить на вопрос «что
сейчас запущено».

### `make update` — применить то, что уже на сервере

```bash
make update SERVER=deploy@<IP>
```

Перезапускает стек из **текущих** образов: `docker compose up -d --no-build`.
Нужен, когда изменилось окружение, а не код — правка `.env`, новый
`Caddyfile`, изменения в `docker-compose.yml`. Образы не собираются и не
везутся: для этого `make deploy`.

### Если цепочку нужно разобрать на части

Шаги доступны и по отдельности — `make images`, `make images-ship
SERVER=…`, `make images-push` (через реестр, если появится CI),
`make deploy-files SERVER=…`. Нужны они только при разборе неполадок:
обычный выпуск — это `make deploy`.

## 3. Справочники

Миграции создают **пустые** таблицы. Города, районы и услуги — справочные
данные, и без них не пройти регистрацию: список городов приходит пустым,
выбрать нечего.

```bash
ssh deploy@<IP> "cd noova && docker compose exec api node dist/scripts/seed-reference.js"
```

Идемпотентно: повторный запуск обновляет существующее и ничего не удаляет.
Гонять после каждого выпуска не нужно — только когда справочник менялся.

Что попадает на прод и что нет:

| | Куда | Почему |
|---|---|---|
| услуги, города, районы | прод | без них не работает регистрация и фильтры |
| анкеты, учётные записи, промо-слоты | только разработка | на проде их создают люди |

Накатывается автоматически: `make deploy` делает это сам после того, как
стек стал healthy, а `make setup` — при первичной настройке стенда.

### Справочник живёт в базе, а в репозиторий возвращается выгрузкой

Города, районы и услуги заводятся из админки — значит их источник база, а не
код. Чтобы полное обнуление сервера их не стёрло, есть обратное направление:

```bash
# на сервере, после правок в админке
docker compose exec api node dist/scripts/export-reference.js
# файл prisma/reference-data.ts забрать к себе и закоммитить
```

Локально то же самое — `pnpm --filter @noova/api db:export:reference`.

**Идентификаторы выгружаются вместе с данными** и проставляются при создании:
справочник, восстановленный на чистой машине, получает те же id. Без этого
всё, что на него ссылается — анкеты из отдельного дампа, ссылки в журналах, —
указывало бы в пустоту.

> **Правки в админке без выгрузки живут до следующего выпуска.** `make deploy`
> накатывает справочник из файла, и отключённый в админке город он включит
> обратно. Порядок работы: поправили в админке → выгрузили → закоммитили.

Источник данных — `prisma/locations.ts`, `prisma/services.ts` и переводы в
`prisma/reference-translations.ts`. Демо-сид (`db:seed`) справочники не
заводит вовсе: он их читает и падает с подсказкой, если они пусты. Выпавшие
из справочника услуги и районы не удаляются, а деактивируются — на них
могут ссылаться анкеты.

**Названия хранятся в БД переводами на три языка** (N-35), и API отдаёт их
по параметру `?locale=`. Неполный перевод не сохраняется: сид падает с
указанием, у какой записи какого языка не хватает.

## 4. Первый администратор

Создаётся разово, после первого успешного выпуска:

```bash
ssh deploy@<IP> "cd noova && docker compose exec api node dist/scripts/create-admin.js <email> '<пароль>'"
```

Запускается **внутри** контейнера `api`: снаружи базы не видно, порт Postgres
наружу не публикуется. Пароль — не короче 10 символов. Повторный запуск на
существующем адресе завершится ошибкой: повысить обычного пользователя до
администратора этот сценарий намеренно не умеет.

## 5. Если выпуск не удался

Сначала — что именно упало. `make deploy` при таймауте печатает хвост логов
сам, но полная картина здесь:

```bash
ssh deploy@<IP> 'cd noova && docker compose logs -f api migrate'
```

Вернуть прошлый образ:

```bash
make rollback SERVER=deploy@<IP> TAG=<тег прошлого выпуска>
```

Автоматического отката при неудаче намеренно нет: миграции к тому моменту
уже применены, и вернуть образ на схему прошлого выпуска — значит получить
код и базу вразнобой. Скрипт печатает готовую команду и оставляет решение
за вами.

Откат кода — это одна строка. **Откат миграции — нет.** Prisma не умеет
автоматически откатывать `migrate deploy`, поэтому миграции, удаляющие
колонки или данные, стоит разносить на два выпуска: сначала перестать
пользоваться, выпустить, убедиться, и только потом удалять. В этом проекте
так уже сделано с `Profile.nationality` — колонка помечена к удалению,
но не удалена.

**Дамп перед миграциями `make deploy` снимает сам** — это первое, что он
делает на сервере. Вручную, когда выпуск идёт не через него:
`make backup`. Другого способа вернуться после неудачной миграции нет.
