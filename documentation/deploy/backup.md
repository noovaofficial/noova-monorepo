# Backup

**На Prod копий не хранится.** Снимок делается в момент запроса и уходит
потоком — от `pg_dump` сразу в ssh, не касаясь диска. Снятие по расписанию,
проверку и хранение ведёт отдельная машина. Подготовка машины — [vps.md](vps.md).

Забирает хранилище, а не отправляет Prod: иначе ключ с правом записи в архив
лежал бы на Prod, и тот, кто его получил, стёр бы заодно и копии.

---

## 1. Ключи шифрования

```bash
./infra/backup/make-key.sh ~/noova-backup           # у себя
scp ~/noova-backup/backup-public.pem deploy@<IP Prod>:noova/
```

Открытая часть уезжает на Prod, закрытая — на Backup (иначе нечем проверять
копии) и к вам. **Третью копию закрытого ключа держите офлайн:** потеряв её,
копии не прочитать никогда.

## 2. Настройка

```bash
make deploy-files SERVER=deploy@<IP Prod>           # скрипты на Prod
make backup-storage STORAGE=deploy@<IP Backup> SERVER=deploy@<IP Prod> \
    KEY=~/noova-backup/backup-private.pem
```

Печатает открытый ключ хранилища и отпечаток ключа Prod. Отпечаток сверьте:

```bash
ssh deploy@<IP Prod> 'ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub'
```

Это единственный момент, когда подмену машины можно заметить.

```bash
make backup-allow-pull SERVER=deploy@<IP Prod> KEY='ssh-ed25519 … noova-pull'
```

Ключу хранилища на Prod доступны ровно две команды: `snapshot-db` и
`snapshot-media`. Ни оболочки, ни записи, ни удаления.

## 3. Уведомления и мониторинг

Внешнего монитора (healthchecks.io) нет: о каждой ночи и о каждой поломке
сообщает Telegram-бот, а тишину — то есть выключенное хранилище, сломанный крон
или ключ — ловит сторож на проде. Обе части описаны ниже, вместе они заменяют
монитор: одной хранилища недостаточно, ведь оно молчит ровно тогда, когда
недоступно.

### 3а. Сообщения хранилища и сторож на проде

Две части, и обе нужны — по одной не хватает:

1. **Хранилище пишет само** — об итоге каждой ночи. `pull.sh` шлёт в Telegram
   «Успешно ✅» с состоянием копий при успехе и «Ошибка ❌» с причиной при
   поломке. Настройка — в `~/noova-pull.env` на хранилище:

   ```bash
   PULL_TG_TOKEN=токен бота от @BotFather
   PULL_TG_CHAT=id чата, куда бот добавлен
   ```

   В сообщении: статус, число копий (по ролям), свежесть, размеры базы и фото,
   свободное место на диске и на сколько копий его ещё хватит (⚠️ при менее
   15% или менее 5 копий, ❌ при менее 5% или менее 2 копий). Отчёт об ошибке
   выглядит так же — с причиной и состоянием копий на диске.

   Без этих двух переменных скрипт молчит, как раньше. Токен передаётся `curl`
   через stdin, а не аргументом, чтобы не светиться в `ps`.

2. **Сторож на проде** (`watch.sh`) — ловит тишину. Хранилище, выключенное или
   со сломанным кроном/ключом, само ничего не напишет. Поэтому при каждой
   выдаче копии `pull-guard.sh` пишет пульс `~/.noova-backup/last-db` и
   `last-media`, а сторож раз в день (09:00 UTC) проверяет его возраст и при
   превышении порога (`WATCH_MAX_HOURS`, по умолчанию 30 ч) пишет в Telegram.
   Доступа к хранилищу сторожу не нужно: ключ к машине с закрытым ключом
   шифрования на проде держать нельзя.

   ```bash
   make deploy-files SERVER=deploy@<IP Prod>            # довезти скрипты
   ssh deploy@<IP Prod> 'bash ~/noova/infra/backup/watch-setup.sh'
   ssh deploy@<IP Prod>                                  # вписать токен и чат:
   nano ~/noova-watch.env                                # WATCH_TG_TOKEN, WATCH_TG_CHAT
   bash ~/noova/infra/backup/watch.sh                    # проверить вручную
   ```

   Пока сторож не получил ни одной выдачи, он молчит первые `WATCH_MAX_HOURS`
   часов после установки, затем тревожит.

Хранилище: довезти новый `pull.sh` можно без пересоздания настроек —
`scp infra/backup/pull.sh deploy@<IP Backup>:` и дописать переменные в
`~/noova-pull.env`.

### 3б. Команды боту: /list, /backup, /verify

Бот живёт на хранилище (`bot.py`, systemd-сервис) и отвечает в той же группе,
куда приходят сообщения о копиях. Команды принимаются **только** из
`PULL_TG_CHAT` и **только** от пользователей из `PULL_TG_ADMINS` (числовые user
id через запятую; свой узнать у @userinfobot). Остальным бот не отвечает
вовсе. Пустой список — бот не стартует.

| Команда | Что делает |
|---|---|
| `/list` | какие копии лежат на хранилище: дата, роль (ежедневная/недельная/месячная), статус проверки, размеры, возраст |
| `/backup` | запускает `pull.sh` сейчас; итог — обычным сообщением. Не чаще раза в 10 минут (`PULL_BOT_COOLDOWN_MIN`) |
| `/verify [метка]` | проверяет копию (по умолчанию свежую), метка вида `20260924T041701Z` из `/list` |
| `/disk` | сколько места свободно на диске хранилища, сколько занято копиями и на сколько ещё копий хватит; предупреждает, когда мало |
| `/help` | справка |

Бот **не умеет** расшифровывать, отдавать файлы и удалять: на машине лежит
закрытый ключ шифрования, поэтому он запускает только `pull.sh` и
`storage-verify.sh` и читает список каталога. Одновременно идёт один запуск:
`pull.sh`, крон и `/verify` берут общий замок `~/.noova-pull.lock`. Команды,
присланные, пока бот был выключен, при старте отбрасываются.

```bash
# на хранилище: в ~/noova-pull.env должны быть PULL_TG_TOKEN, PULL_TG_CHAT,
# PULL_TG_ADMINS; рядом лежат bot.py, bot-setup.sh, pull.sh, storage-verify.sh
bash ~/bot-setup.sh                       # нужны python3, flock, sudo
sudo journalctl -u noova-backup-bot -f    # логи
```

### 3в. Нагрузка сервера

Сторож на проде заодно следит за нагрузкой: `load-sample.sh` каждые 10 минут
пишет замер в `~/.noova-backup/load.log` (load average, память, диск, CPU каждого
контейнера), хранит 8 суток. Ставится тем же `watch-setup.sh`.

- **Суточный отчёт** приходит вместе со сторожем (09:00 UTC): среднее и пик за 24 часа
  по нагрузке CPU, памяти и диску, пик по контейнерам, цвет 🟢🟡🔴. Отключается
  `WATCH_LOAD_REPORT=0` в `~/noova-watch.env`.
- **Тревоги** из `load-sample.sh`: CPU выше `LOAD_ALERT_CPU_PCT` (80%) три замера
  подряд, память выше `LOAD_ALERT_MEM_PCT` (90%), диск выше `LOAD_ALERT_DISK_PCT`
  (85%). Не чаще раза в `LOAD_ALERT_COOLDOWN_H` часов (6) на вид тревоги.
- «Нагрузка CPU» — это load average за минуту, делённый на число ядер: 100% —
  все ядра заняты, выше — процессы стоят в очереди. Не процент процессора.

Обновить на проде: `make deploy-files SERVER=…`, затем
`bash ~/noova/infra/backup/watch-setup.sh` (пересоздаёт крон, настройки не трогает),
допишите новые переменные в `~/noova-watch.env` (шаблон в watch-setup.sh).

## 4. Проверить

```bash
ssh deploy@<IP Backup> 'bash ~/pull.sh'             # весь цикл прямо сейчас
make backup-storage-check STORAGE=deploy@<IP Backup>
```

---

## Что происходит каждую ночь

1. Хранилище просит снимок — сначала базу, потом фотографии — и принимает
   потоком. Порядок важен: лишний файл в архиве безвреден, отсутствующий нет.
2. Проверяет: расшифровывает, разжимает, считает таблицы и строки, разбирает
   архив и сверяет число фотографий с **живыми** строками в `Photo`. Мягко
   удалённые (`deletedAt`) не в счёт: файлы стираются сразу при удалении, и
   строка без файлов у них ожидаема.
3. И **только если свежая копия прошла проверку** — удаляет лишнее.

Проверка идёт потоком, без Postgres и Docker: на диск не попадает ничего,
кроме списка имён из архива. Хватает слабой машины.

Не ловится только дамп, который разжимается, но не разворачивается из-за
ошибки в SQL, — это показывает `make backup-check` у вас, раз в месяц.

**Остаётся:** две последних копии, самая свежая за прошлую неделю и самая
свежая за прошлый месяц. Не больше четырёх. Меняется через `PULL_KEEP_DAILY`
в `~/noova-pull.env`.

> Пока хранилище недоступно, копии не делаются **нигде**: на Prod ничего не
> накапливается «до лучших времён».

## Забрать и проверить у себя

```bash
make backup-fetch SERVER=deploy@<IP Prod> DIR=~/noova-backup   # разово, потоком

make infra-up                                       # нужен стенд
make backup-check DIR=~/noova-backup                # свежая пара
make backup-check DIR=~/noova-backup STAMP=20260901T133913Z
```

Разворачивает дамп в **отдельную** базу и сверяет фотографии с `Photo`.
Расшифрованные файлы живут во временном каталоге и удаляются на выходе.

Меньше фотографий, чем живых строк, — отказ. Больше — норма: снимок базы
делается раньше архива.

## Восстановить

```bash
# 1. расшифровать у себя
make backup-open FILE=~/noova-backup/noova-<stamp>.sql.gz.enc \
                 KEY=~/noova-backup/backup-private.pem
make backup-open FILE=~/noova-backup/noova-media-<stamp>.tar.gz.enc \
                 KEY=~/noova-backup/backup-private.pem

# 2. отвезти на Prod
scp ~/noova-backup/noova-<stamp>.sql.gz ~/noova-backup/noova-media-<stamp>.tar.gz \
    deploy@<IP Prod>:noova/

# 3. на Prod: сначала база, потом фотографии
ssh deploy@<IP Prod>
cd ~/noova
./infra/backup/restore.sh noova-<stamp>.sql.gz
./infra/backup/restore-media.sh noova-media-<stamp>.tar.gz
rm -f noova-<stamp>.sql.gz noova-media-<stamp>.tar.gz
```

Скриптами, а не `make`: на сервере `Makefile` нет, туда уезжают только compose,
Caddyfile и `infra/backup/*.sh`.

Обе операции разрушительные и требуют `yes`. Восстановление фото останавливает
`minio` на время распаковки. Открытые копии на Prod удалить — они не должны
там оставаться.

### Чего в копии нет

| | Последствие |
|---|---|
| Redis | все разлогинены, очередь писем `mail:queue` теряется |
| TLS-сертификаты | Caddy выпустит заново |
| DKIM-ключ | живёт на релее, переносится отдельно ([smtp.md](smtp.md)) |
| `.env` | хранить рядом с копией: без `IP_HASH_SALT` журналы теряют историю |

## Если что-то не так

| Симптом | Причина |
|---|---|
| `снимок базы не удался` | Prod недоступен, не выполнен `make backup-allow-pull`, или нет `stream.sh` (`make deploy-files`) |
| `не отвечает …` на хранилище | сменился ключ хоста Prod: удалить строку из `~/.ssh/known_hosts` на Backup и повторить `backup-storage` |
| `pull-guard: разрешены только snapshot-db и snapshot-media` | ключ хранилища используют для чего-то ещё — так и задумано |
| `Дамп оборван: нет завершающей строки pg_dump` | `pg_dump` упал на середине передачи |
| `Фотографий в архиве меньше, чем живых строк в базе` | часть файлов потерялась в MinIO, копия непригодна. Мягко удалённые фотографии в сверку не входят |
| `Дамп не расшифровался. Тот ли ключ?` | на Backup закрытая часть не от той пары, которой шифрует Prod |
| `самой свежей копии N ч` | цикл не отработал, смотреть `~/noova-pull.log` на Backup |
