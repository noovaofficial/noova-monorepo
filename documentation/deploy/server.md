Что купить, как настроить домен, как подготовить машину и как заставить

## 1. Что нужно, кроме сервера

Почти всё внутри стека: хранилище файлов (MinIO), база, Redis и TLS —
свои. Снаружи нужны немногие вещи, и для стенда разработки — ещё меньше.

| | Стенд | Прод | Комментарий |
|---|---|---|---|
| Домен и DNS | нужен | нужен | Njalla подходит |
| Сервер | 4 ГБ / 2 vCPU | 8 ГБ / 4 vCPU | см. §2 |
| Порт 25 наружу | нужен | нужен | иначе не уходит почта |
| PTR (обратный DNS) | желателен | нужен | ставит провайдер, не в DNS-панели |
| SPF, DKIM, DMARC | желательны | нужны | см. §4 |
| Тайл-сервер карт | можно без | нужен | L-06 в `legal.md` |
| Платёжный процессор | нет | нужен | вместе с N-30 |
| Место для бэкапов вне сервера | желательно | обязательно | N-29 |
| Хранилище файлов | своё | своё | MinIO в стеке |
| TLS-сертификат | Caddy | Caddy | бесплатно, автоматически |

**Ничего платного, кроме домена и сервера, для стенда не требуется.**

### Домен на Njalla

Njalla регистрирует домен **на себя** и передаёт право пользования — в этом
и смысл сервиса, но помните: в реестре владелец не вы, и перенос к другому
регистратору позже будет отдельной процедурой. Их DNS годится.

### Записи DNS

| Тип | Имя | Значение | Когда |
|---|---|---|---|
| A | `@` | IPv4 сервера | сразу |
| A | `mail` | IPv4 сервера | сразу |
| TXT | `@` | `v=spf1 a mx ~all` | сразу |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:<ящик вне домена>` | сразу |
| TXT | `mail._domainkey` | из контейнера | после первого запуска, §4 |

**`AAAA` не добавляйте**, пока IPv6 не проверен отдельно. Причина не в
экономии записей: лишняя `AAAA` ломает три вещи разом.

- Docker не публикует порты по IPv6 без явной настройки демона. Запись
  есть, слушателя нет — IPv6-клиенты получают отказ, и выглядит это как
  «сайт лежит у части посетителей».
- Let's Encrypt при наличии `AAAA` ходит на проверку по IPv6 в первую
  очередь. Не ответил — **сертификат не выпустится вообще**, включая IPv4.
- PTR провайдер ставит на один адрес. Если Postfix уйдёт наружу с IPv6 без
  обратной записи, письма начнут отклонять на входе.

IPv4 покрывает всех посетителей. Возвращаться к IPv6 стоит отдельной
задачей: сначала `ip6tables` в демоне Docker, потом `AAAA`, потом PTR на
IPv6, и только затем проверка почты заново.

В `rua` ставьте ящик **вне этого домена**: MX на приём стек не поднимает,
и отчёты на `admin@<домен>` никуда не придут.

### Выбор провайдера

Главный критерий — **не приём криптовалюты, а правила по содержимому**.
Крипту берут многие; приостановка учётной записи из-за взрослого каталога
опаснее любой DDoS-атаки: сайт не просто ляжет, пропадёт доступ к машине
с данными.

До оплаты найдите в условиях провайдера явное разрешение на adult-контент
и убедитесь, что нет оговорки «по нашему усмотрению». Отдельно спросите про
**порт 25** — многие закрывают его по умолчанию, а некоторые не открывают
вовсе. Проверять это надо до оплаты, а не после переезда.

Правовая сторона выбора юрисдикции — L-09 в `legal.md`.

## 2. Мощности

Девять контейнеров: postgres, redis, minio, api, web, caddy, smtp, jobs,
backup.

- **RAM 4 ГБ — минимум, не запас.** У `api` стоит потолок 768 МБ
  (`under-pressure` отдаёт 503 вместо падения по памяти), Next в standalone
  берёт 200–300 МБ, Postgres около 256 МБ, столько же MinIO. Обработка фото
  через sharp даёт короткие всплески. На 2 ГБ стек заведётся, но начнёт
  свопить на первой же загрузке снимков.
- **Диск.** Три размера на снимок в WebP — примерно 300 КБ на фотографию,
  до 20 фото на анкету, то есть около 6 МБ. Тысяча анкет ≈ 6 ГБ плюс дампы.
  80 ГБ NVMe хватит надолго.

## 3. Подготовка сервера

Чистая машина от провайдера к запуску стека не готова: нужен непривилегированный
пользователь, Docker, закрытый периметр и своп.

```bash
# 0. СНАЧАЛА — свой ключ на сервер, пока пароль ещё принимается.
#    Выполняется у СЕБЯ на машине, не на сервере.
#    Провайдеры отдают машину с парольным входом; если пропустить этот шаг
#    и сразу выключить пароли (шаг 2), заходить будет нечем.
ssh-copy-id -i ~/.ssh/<ваш-ключ>.pub root@<IP>
ssh root@<IP>            # должно пустить БЕЗ пароля — только после этого дальше

# 1. Пользователь вместо root
adduser deploy && usermod -aG sudo deploy
# Копируем ключ root новому пользователю. Работает только если шаг 0 сделан:
# иначе копировать нечего, и это тихо пройдёт «успешно».
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

# 2. Закрыть вход root и пароли — см. врезку ниже, там есть подвох
sshd -T | grep -E 'permitrootlogin|passwordauthentication'   # что действует сейчас

# 3. Docker
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy

# 4. Периметр. Порт 25 наружу нужен исходящий — входящий не нужен:
#    контейнер smtp только отправляет и портов не публикует.
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable

# 5. Своп — независимо от тарифа
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

Своп нужен не как замена памяти, а как страховка от пиков: обработка фото
через `sharp` даёт короткие всплески, и без свопа их встречает OOM-killer —
посреди загрузки снимков.

### Про шаг 2: SSH закрывается не так очевидно, как кажется

**Менять значение, а не комментировать строку.** Закомментированная
директива не выключается — возвращается умолчание OpenSSH, а умолчания
здесь ровно противоположны нужному: `PermitRootLogin` → `prohibit-password`
(root по ключу по-прежнему заходит), `PasswordAuthentication` → `yes`.
Закомментировать `PasswordAuthentication yes` — значит оставить пароли
включёнными и думать, что выключил.

```
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
```

`KbdInteractiveAuthentication` нужен третьим: без него на части образов
пароль всё ещё принимается вторым путём, через PAM.

**Главный подвох — не в этом файле.** В начале `/etc/ssh/sshd_config` у
Ubuntu и Debian стоит `Include /etc/ssh/sshd_config.d/*.conf`, а провайдеры
кладут туда свои файлы вроде `50-cloud-init.conf` с
`PasswordAuthentication yes`. Побеждает **первое** встреченное значение, то
есть включённый Include в начале перекрывает вашу правку ниже по файлу.
Именно поэтому «я всё выключил, а пароль всё равно работает».

```bash
grep -rE 'PermitRootLogin|PasswordAuthentication' /etc/ssh/sshd_config.d/
```

Нашлось — правьте там же или удаляйте файл.

**Проверять только по действующей конфигурации**, а не по тому, что
написано в файлах:

```bash
sshd -t                                     # синтаксис; молчит — значит цел
sshd -T | grep -E 'permitrootlogin|passwordauthentication|kbdinteractive'
systemctl restart ssh
```

Ожидаемый вывод — `permitrootlogin no`, `passwordauthentication no`,
`kbdinteractiveauthentication no`.

### Если вход уже потерян

Симптом — `Permission denied (publickey)` и под `deploy`, и под `root`,
причём в выводе `ssh -v` видно `Authentications that can continue: publickey`.
Значит пароли выключены, а ключа на сервере нет: шаг 0 был пропущен.

**Не закрывайте старую сессию, если она ещё открыта** — это самый дешёвый
путь. Прямо в ней:

```bash
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
echo '<содержимое вашего .pub>' >> /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
```

Проверять — **новым окном**, не закрывая текущее: `ssh deploy@<IP>`.

Сессии нет — остаётся консоль в панели провайдера (VNC). Она идёт мимо SSH
и работает всегда; дальше те же команды.

### Root после этого

Закрывается не root, а **вход под ним по сети**. Права остаются доступны
двумя путями:

```bash
ssh deploy@<IP>      # обычный вход
sudo -i              # root-шелл, когда он нужен
```

Второй путь — аварийный: консоль в панели провайдера. Она идёт мимо SSH,
поэтому переживает любую поломку конфигурации. Это и есть причина, по
которой закрывать root по сети безопасно.

Для повседневных задач root не нужен вовсе: `deploy` состоит в группе
`docker`, а значит `docker compose` и `make deploy` работают без `sudo`.

**Перед тем как закрыть root, проверьте, что замена работает.** Порядок
проверок именно такой — каждая следующая имеет смысл только после
предыдущей:

```bash
# 1. вторым окном, не закрывая текущее
ssh deploy@<IP>
# 2. права
sudo -v          # спросит пароль пользователя deploy
# 3. docker без sudo (после перелогина — членство в группе даётся на входе)
docker ps
```

`sudo -v` здесь не формальность: если при `adduser` пароль не задавался,
`sudo` не сработает, и `PermitRootLogin no` оставит машину без пути к
правам вообще — кроме консоли провайдера. Пароль ставится через
`passwd deploy`.

**Прежнюю сессию не закрывайте**, пока все три проверки не прошли. Ошибка
в конфигурации SSH — единственная правка из всего развёртывания, которая
запирает вас снаружи машины.

## 4. Почта

Мы поднимаем **свой Postfix** (контейнер `smtp`): SendGrid, Mailgun и
подобные ограничивают взрослый контент в условиях использования (решение
из N-15). Плата за это — настройка доставляемости вручную.

Без почты не пройти регистрацию: подтверждение адреса и сброс пароля
уходят письмом.

**1. Исходящий порт 25.** Самая частая причина «письма не приходят».
Большинство провайдеров закрывает его по умолчанию (у Zomro — п. 5.33
оферты), открывается заявкой в поддержку. Входящий 25-й не нужен.

**2. PTR-запись** для IP → `mail.<домен>`. Ставится у провайдера, **не**
в DNS-панели. Без неё большинство почтовых серверов отправит письма в спам.

**3. Записи DNS** — таблица в §1. К почте относятся `A mail`, `TXT @` (SPF),
`TXT _dmarc` и `TXT mail._domainkey` (DKIM, добавляется после первого запуска).

DKIM-ключ генерируется сам при первом запуске (`DKIM_AUTOGENERATE`).
Публичную часть достать так:

```bash
docker compose exec smtp sh -c 'ls -R /etc/opendkim/keys && cat /etc/opendkim/keys/*/*.txt'
```

Содержимое `.txt` — готовая DNS-запись.

**Проверьте репутацию IP** до того, как привязывать домен: свежий адрес
нередко уже в чёрных списках от прежнего арендатора, и менять его после
настройки всего остального — потерянный день. Проверка — Blocklist Removal
Center на `spamhaus.org`.

**Проверка после настройки.** Зарегистрируйтесь на сайте и убедитесь, что
письмо дошло не в спам. `mail-tester.com` за один прогон покажет, что из
SPF, DKIM, DMARC и PTR не сходится.
