## 1. Что нужно снаружи

База, Redis, хранилище файлов (MinIO) и TLS — внутри стека. Снаружи:

| | Стенд | Прод | Комментарий |
|---|---|---|---|
| Домен и DNS | нужен | нужен | Njalla подходит |
| Сервер | 4 ГБ / 2 vCPU | 8 ГБ / 4 vCPU | §2 |
| Исходящий порт 25 | нужен | нужен | иначе не уходит почта |
| PTR | желателен | нужен | ставит провайдер, не в DNS-панели |
| SPF, DKIM, DMARC | желательны | нужны | §4 |
| Тайл-сервер карт | можно без | нужен | L-06 в `legal.md` |
| Платёжный процессор | нет | нужен | N-30 |
| Бэкапы вне сервера | желательно | обязательно | N-29 |

### Выбор провайдера

До оплаты проверьте два пункта: явное разрешение adult-контента в условиях
(без оговорки «по нашему усмотрению») и открытый исходящий порт 25. Первое —
потому что приостановка учётной записи отнимает доступ к машине с данными.
Второе — потому что многие не открывают его вовсе. Юрисдикция — L-09 в
`legal.md`.

Njalla регистрирует домен на себя: в реестре владелец не вы, перенос к
другому регистратору — отдельная процедура.

### Записи DNS

| Тип | Имя | Значение | Когда |
|---|---|---|---|
| A | `@` | IPv4 сервера | сразу |
| A | `mail` | IPv4 сервера | сразу |
| TXT | `@` | `v=spf1 a ip4:<IP> ~all` | сразу |
| TXT | `_dmarc` | `v=DMARC1; p=none; rua=mailto:<ящик вне домена>` | сразу |
| TXT | `mail._domainkey` | из контейнера | после первого запуска, §4 |

- SPF-запись должна быть **одна**: две записи `v=spf1` дают `permerror`, и
  проверка не проходит вовсе.
- `rua` — ящик **вне этого домена**: MX на приём стек не поднимает, отчёты
  на `admin@<домен>` никуда не придут.
- **`AAAA` не добавляйте**, пока IPv6 не настроен отдельно. Docker без явной
  настройки демона по IPv6 не слушает — «сайт лежит у части посетителей».
  Let's Encrypt при наличии `AAAA` проверяет IPv6 первым, и сертификат не
  выпустится вообще, включая IPv4. PTR провайдер ставит на один адрес, так
  что письма с IPv6 начнут отклонять. Порядок возврата к IPv6, если
  понадобится: `ip6tables` в демоне → `AAAA` → PTR на IPv6 → проверка почты
  заново.

## 2. Мощности

Девять контейнеров: postgres, redis, minio, api, web, caddy, smtp, jobs, backup.

- **RAM 4 ГБ — минимум, не запас.** `api` ограничен 768 МБ, Next в standalone
  берёт 200–300 МБ, Postgres и MinIO — по 256 МБ, обработка фото через sharp
  даёт всплески. На 2 ГБ стек заведётся и начнёт свопить на первой загрузке.
- **Диск.** Около 6 МБ на анкету (три размера в WebP, до 20 фото). Тысяча
  анкет ≈ 6 ГБ плюс дампы; 80 ГБ NVMe хватит надолго.

## 3. Подготовка сервера

```bash
# 0. Свой ключ — руками и первым делом, пока пароль ещё принимается
ssh-copy-id -i ~/.ssh/<ваш-ключ>.pub root@<IP>
ssh root@<IP>                       # должно пустить БЕЗ пароля

# 1–5. Всё остальное
make server-setup SERVER=root@<IP>
```

Шаг 0 ручной намеренно: без ключа у root скрипт откажется выключать парольный
вход. Иначе он запер бы машину снаружи — единственная ошибка развёртывания,
которую нельзя исправить по сети.

Скрипт `infra/server/setup.sh` идемпотентен, проверяет результат по `sshd -T`
и откатывает свою правку при неудачной проверке.

После него: `passwd deploy`, затем **вторым окном**, не закрывая текущее,
проверить три вещи по порядку — `ssh deploy@<IP>`, `sudo -v`, `docker ps`.
Без пароля у `deploy` команда `sudo` не сработает, и `PermitRootLogin no`
оставит машину без пути к правам.

### То же вручную

```bash
# 0. СНАЧАЛА ключ на сервер, у СЕБЯ на машине. Пропустить нельзя:
#    после шага 2 заходить будет нечем.
ssh-copy-id -i ~/.ssh/<ваш-ключ>.pub root@<IP>
ssh root@<IP>            # должно пустить БЕЗ пароля

# 1. Пользователь вместо root
adduser deploy && usermod -aG sudo deploy
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

# 2. Закрыть вход root и пароли — см. ниже
sshd -T | grep -E 'permitrootlogin|passwordauthentication'

# 3. Docker
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy

# 4. Периметр. Порт 25 нужен только исходящий: контейнер smtp
#    портов не публикует.
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable

# 5. Своп — страховка от всплесков sharp, иначе их встречает OOM-killer
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
```

### Шаг 2: два подвоха

**Менять значение, а не комментировать строку.** Закомментированная директива
возвращает умолчание OpenSSH, а они здесь противоположны нужному:
`PermitRootLogin` → `prohibit-password`, `PasswordAuthentication` → `yes`.

```
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
```

Третья строка обязательна: без неё на части образов пароль принимается через PAM.

**`Include` в начале `sshd_config` перекрывает правку.** Провайдеры кладут в
`/etc/ssh/sshd_config.d/` файлы вроде `50-cloud-init.conf` с
`PasswordAuthentication yes`, а побеждает первое встреченное значение. Отсюда
«я всё выключил, а пароль всё равно работает».

```bash
grep -rE 'PermitRootLogin|PasswordAuthentication' /etc/ssh/sshd_config.d/
```

Нашлось — правьте там же или удаляйте файл. Проверять только по действующей
конфигурации:

```bash
sshd -t                                     # синтаксис; молчит — значит цел
sshd -T | grep -E 'permitrootlogin|passwordauthentication|kbdinteractive'
systemctl restart ssh
```

Ожидается `no` во всех трёх.

### Если вход потерян

Симптом — `Permission denied (publickey)` под обоими пользователями: пароли
выключены, ключа нет, шаг 0 пропущен. В открытой сессии, если она осталась:

```bash
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
echo '<содержимое вашего .pub>' >> /home/deploy/.ssh/authorized_keys
chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys
```

Сессии нет — консоль в панели провайдера (VNC), она идёт мимо SSH. Она же
причина, по которой закрывать root по сети безопасно. Для повседневных задач
root не нужен: `deploy` состоит в группе `docker`.

## 4. Почта

Свой Postfix в контейнере `smtp`: массовые сервисы ограничивают взрослый
контент в условиях использования (N-15). Без почты не пройти регистрацию —
подтверждение адреса и сброс пароля уходят письмом.

**1. Проверьте репутацию IP до всего остального** — Blocklist Removal Center
на `spamhaus.org`. Свежий адрес нередко уже в чёрных списках от прежнего
арендатора, и менять его после настройки остального — потерянный день.

**2. Исходящий порт 25.** Самая частая причина «письма не приходят».
Большинство провайдеров закрывает его по умолчанию, открывается заявкой в
поддержку. Входящий не нужен. Проверка с сервера:

```bash
timeout 8 bash -c 'exec 3<>/dev/tcp/aspmx.l.google.com/25 && head -1 <&3'
```

Ответ `220 ... ESMTP` — открыт. Молчание — закрыт.

**3. PTR-запись** IP → `mail.<домен>`. Ставится у провайдера, **не** в
DNS-панели. Без неё письма уходят в спам. Проверка: `dig +short -x <IP>`.

**4. DNS** — таблица в §1: `A mail`, SPF, DMARC.

**5. DKIM.** Ключ генерируется сам при первом запуске (`DKIM_AUTOGENERATE`).
Публичная часть:

```bash
docker compose exec smtp ls -la /etc/opendkim/keys/
docker compose exec smtp cat /etc/opendkim/keys/<домен>.txt
```

Файлы лежат плоско (`<домен>.private`, `<домен>.txt`), без подкаталога.
В DNS идёт запись `mail._domainkey` со значением из **склеенных подряд**
кусков в кавычках — без самих кавычек, скобок и комментария после `;`.
Значение длиннее 255 символов, панель регистратора разбивает его сама.

**Проверка.** Зарегистрируйтесь на сайте: письмо должно прийти не в спам.
`mail-tester.com` за один прогон покажет, что из SPF, DKIM, DMARC и PTR не
сходится.

### Если порт 25 не откроют

Так и вышло у vps.ac: «closed in order to prevent spam», открывать не будут.
Внешний ESP не подходит — SendPulse, Postmark, Resend, Brevo и подобные
запрещают тематику каталога в AUP. Postfix переезжает на вторую машину у
провайдера, который 25-й держит открытым.

Порядок целиком — [mail.md](mail.md).
