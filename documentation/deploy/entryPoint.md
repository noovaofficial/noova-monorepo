## 1. Как посмотреть базу

### Быстро, прямо на сервере

```bash
# список таблиц
docker compose exec postgres psql -U noova -d noova -c '\dt'

# сколько строк в каждой
docker compose exec postgres psql -U noova -d noova -c \
  "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc;"

# произвольный запрос
docker compose exec postgres psql -U noova -d noova -c \
  "select slug, status from \"Profile\" limit 20;"

# интерактивно
docker compose exec -it postgres psql -U noova -d noova
```

Полезное в `psql`: `\dt` — таблицы, `\d "Profile"` — колонки таблицы,
`\q` — выход.

### Графически, через Prisma Studio

**Порт наружу не открывать.** Пробросьте его по SSH и откройте у себя:

```bash
ssh -L 5555:localhost:5555 user@сервер
# в другом терминале, на сервере:
docker compose exec api npx prisma studio --port 5555
```

Дальше `http://localhost:5555` у себя в браузере. Соединение идёт по SSH,
наружу ничего не смотрит.

> Открытый порт Postgres или Studio наружу — прямой доступ ко всей базе
> с особой категорией персональных данных. Только SSH-туннель.

## 2. Бэкапы

Внутри стека контейнер `backup` делает `pg_dump` по расписанию
(`BACKUP_INTERVAL_SECONDS`, по умолчанию раз в сутки) в `./backups/`, с
ротацией на `BACKUP_KEEP_DAYS` дней. Дамп пишется во временный файл и
переименовывается в конце — оборванный процесс не оставит битый файл,
выглядящий как валидный.

Этого мало: **дамп на том же диске защищает от кривой миграции, но не от
потери сервера**, а потеря сервера и есть главный риск. DDoS данные не
стирает — их стирают приостановка провайдером, отказ диска и ошибка
оператора.

### Разовая подготовка

```bash
./infra/backup/make-key.sh ~/noova-backup            # у себя
scp ~/noova-backup/backup-public.pem deploy@<IP>:noova/
```

Открытым ключом шифруют на сервере, закрытый остаётся у вас. **Ключ не
должен лежать на той же машине**: иначе шифрование защищает ровно от того,
чего не случится.

### Снять копию и забрать

```bash
make backup-fetch SERVER=deploy@<IP> DIR=~/noova-backup
```

Одной командой: дамп базы, затем архив фотографий, затем шифрование обоих
и скачивание. Открытые файлы на сервере не остаются.

**Порядок не случаен: сначала база, потом фотографии.** Снимок между ними
добавит файл, на который в базе нет строки, — это безвредно. Обратный
порядок дал бы строку без файла, то есть битую анкету.

### Прочитать и проверить

```bash
make backup-open FILE=~/noova-backup/noova-<stamp>.sql.gz.enc \
                 KEY=~/noova-backup/backup-private.pem
make backup-verify FILE=~/noova-backup/noova-<stamp>.sql.gz
```

`backup-verify` разворачивает дамп в **отдельную** базу и показывает число
таблиц, анкет и фотографий. Текущие данные не трогает: проверка, ради
которой нужно рискнуть рабочей базой, не будет сделана ни разу — а
непроверенный бэкап это не бэкап.

Число фотографий из этого вывода сравните с содержимым архива:

```bash
tar tzf ~/noova-backup/noova-media-<stamp>.tar.gz | wc -l
```

### Восстановление

```bash
make restore DUMP=backups/noova-<stamp>.sql.gz          # база
make restore-media ARCHIVE=noova-media-<stamp>.tar.gz   # фотографии
```

Обе команды разрушительные и требуют подтверждения `yes`. Восстановление
фотографий останавливает `minio` на время распаковки: MinIO держит файлы
открытыми, и распаковка под работающим контейнером оставила бы часть старых
объектов вперемешку с новыми.

> Дампы содержат персональные данные особой категории по GDPR. Каталог
> `backups/` в git не попадает; копии шифруются до того, как покидают
> машину.

## 3. Переезд на другой домен

Поменять `SITE_DOMAIN` / `SITE_URL` в `.env` на сервере и перезапустить:
`docker compose up -d --force-recreate caddy web`. Сертификат выпустится сам.

Адреса запекаются в браузерный бандл на сборке, поэтому вместе с этим
обновите `.env.deploy` у себя и выпустите заново — иначе фронт продолжит
ходить на старый домен. Подробности — [release.md](release.md) §1.
