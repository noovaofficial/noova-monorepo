## 1. База

```bash
docker compose exec postgres psql -U noova -d noova -c '\dt'
docker compose exec postgres psql -U noova -d noova -c \
  "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc;"
docker compose exec -it postgres psql -U noova -d noova
```

`\dt` — таблицы, `\d "Profile"` — колонки, `\q` — выход.

Prisma Studio — **только через SSH-туннель**, порт наружу не открывать:

```bash
ssh -L 5555:localhost:5555 deploy@<IP>
docker compose exec api npx prisma studio --port 5555   # на сервере
```

Дальше `http://localhost:5555` у себя.

> Открытый наружу порт Postgres или Studio — прямой доступ ко всей базе
> с особой категорией персональных данных.

## 2. Бэкапы

**На сервере копий не хранится.** Снимок делается в момент запроса и уходит
потоком — от `pg_dump` сразу в ssh, не касаясь диска. Всё остальное — снятие по
расписанию, проверка, хранение — живёт на отдельной машине-хранилище.

Раньше на сервере работал контейнер `backup`, писавший дампы в `./backups/`.
Он убран: копия на том же диске от потери сервера не спасает, а дамп — это вся
база персональных данных особой категории, лежащая на машине, которая смотрит
наружу.

### Разовая подготовка

```bash
./infra/backup/make-key.sh ~/noova-backup            # у себя
scp ~/noova-backup/backup-public.pem deploy@<IP>:noova/
```

Закрытый ключ остаётся у вас — на прод-сервере ему делать нечего. Исключение
одно: машина-хранилище, где без него не проверить копии (см. ниже).

### Снять копию себе разово

```bash
make backup-fetch SERVER=deploy@<IP> DIR=~/noova-backup
```

Нужно, например, перед рискованной миграцией; обычные ежедневные копии делает
хранилище. База → фотографии, шифрование по дороге, на сервере не остаётся
ничего. Порядок важен: снимок между базой и фото добавит файл без строки
(безвредно), обратный порядок дал бы строку без файла.

### Ежедневный вывоз на вторую машину

Снимок делает крон на проде, а забирает его **хранилище само** — по ssh, ключом,
которому на проде разрешены ровно две команды: список копий и выдача файла.

Направление принципиально. Если бы копии отправлял прод, ключ с правом записи в
архив лежал бы на проде — и тот, кто получил прод, стёр бы вместе с ним и архив,
то есть ровно то, ради чего копии и вывозят наружу.

Порядок (сначала `make deploy-files`, чтобы скрипты были на сервере):

```bash
ssh-copy-id -i ~/.ssh/<ваш ключ>.pub root@<IP хранилища>   # до всего остального
make server-setup SERVER=root@<IP хранилища> ROLE=storage
make backup-storage STORAGE=deploy@<IP хранилища> SERVER=deploy@<IP прода> \
    KEY=~/noova-backup/backup-private.pem
make backup-allow-pull SERVER=deploy@<IP прода> KEY='ssh-ed25519 … noova-pull'
```

`ROLE=storage` — та же подготовка машины, что и для прода (пользователь
`deploy`, вход только по ключу, root и пароли закрыты, своп), но без Docker и
без открытых 80/443: контейнеров здесь нет, публиковать нечего, а лишний порт
на машине с закрытым ключом — площадь атаки в обмен ни на что. Заодно
доставляются `cron`, `openssl` и `curl`, без которых копии молча не поедут.

Расписания на сервере нет: снимок инициирует хранилище, у него же и крон.

Второй шаг печатает открытый ключ хранилища и отпечаток ключа прода. Отпечаток
сверьте с тем, что показывает на самом проде `ssh-keygen -lf
/etc/ssh/ssh_host_ed25519_key.pub`: это единственный момент, когда подмену вообще
можно заметить. Третий шаг принимает напечатанный ключ как есть.

Не дожидаясь ночи:

```bash
ssh <user>@<IP хранилища> 'bash ~/pull.sh'    # весь цикл прямо сейчас
make backup-storage-check STORAGE=<user>@<IP хранилища>
```

#### Что происходит каждую ночь

1. Хранилище просит у сервера снимок — сначала базу, потом фотографии — и
   принимает оба потоком в свой каталог.
2. Проверяет их — расшифровывает, разжимает, считает таблицы и строки,
   разбирает архив фотографий и сверяет их число со строками в `Photo`.
3. И **только если свежая копия проверку прошла** — удаляет лишнее.

Если снимок фотографий не удался, уже принятый дамп удаляется: половина пары
бесполезна, восстановить по ней анкеты целиком нельзя.

Проверка идёт потоком, без Postgres и Docker: расшифровать → разжать →
посчитать → выбросить. На диск не попадает ничего, кроме списка имён из архива,
поэтому расшифрованных персональных данных там не остаётся даже на время
проверки. Хранилищу хватает слабой машины.

Ловится: неподходящий ключ, порча файла, оборванный на середине `pg_dump`,
пропавшие фотографии, расхождение с базой. Не ловится дамп, который разжимается,
но не разворачивается из-за ошибки в самом SQL — это показывает только
восстановление в настоящую базу, то есть `make backup-check` у вас, раз в месяц.

#### Сколько чего хранится

| Где | Что | Сколько живёт |
|---|---|---|
| прод | ничего | — |
| хранилище, `~/backups` | две последних, одна недельная, одна месячная | до 4 копий |

> Обратная сторона: пока хранилище недоступно, копии не делаются **нигде**.
> На сервере ничего не копится «до лучших времён» — собирать потом будет
> нечего. Поэтому неудачную ночь важно замечать (см. ниже про монитор).

На хранилище остаётся ровно: две самых свежих копии, самая свежая из оставшихся
за прошлую неделю или раньше, самая свежая из оставшихся за прошлый месяц или
раньше. В начале недели «недельная» оказывается лишь на день-два старше
вчерашней — так устроен календарь, одна недельная копия большей глубины не даёт.
Число ежедневных меняется через `PULL_KEEP_DAILY` в `~/noova-pull.env`.

> Копия, не прошедшая проверку, помечается файлом `.bad` и не удаляется:
> разбираться с ней проще, пока она есть. Пока непригодна **свежая** копия,
> ротация не запускается вовсе — старое остаётся нетронутым.

#### Закрытый ключ на хранилище

Проверять копию, не расшифровав её, невозможно, поэтому закрытый ключ лежит на
хранилище — иначе автоматической проверки не будет вовсе. Следствие: взлом
хранилища открывает персональные данные, и шифрование самих файлов там уже ни от
чего не защищает.

Отсюда требования к этой машине: ничего, кроме приёма копий, наружу не смотрит,
вход только по ключу, посторонних пользователей и сервисов нет. И ключ должен
остаться ещё в одном месте, кроме хранилища и вашего ноутбука — потеряв обе
копии закрытой части, копии не прочитать уже никогда.

#### Чтобы узнать о поломке

Молчание не означает, что всё хорошо. `pull.sh` завершается ошибкой, если копий
нет, если свежая старше `PULL_MIN_FRESH_HOURS` (26 ч) или если проверка не
прошла, и пишет в `~/noova-pull.log`. Чтобы узнавать об этом, не заходя на
машину, задайте в `~/noova-pull.env` переменную `PULL_PING_URL`
(healthchecks.io и подобные): пинг уходит только после полностью успешной ночи,
поэтому тревогу поднимает сама тишина.

### Проверить

```bash
make infra-up                       # нужен стенд: дамп разворачивается в него
make backup-check                   # свежая копия в ~/noova-backup
make backup-check STAMP=20260829T145907Z
```

Расшифровывает пару, разворачивает дамп в **отдельную** базу, считает объекты
в архиве и сверяет их с числом строк в `Photo`. Расшифрованные файлы живут во
временном каталоге и удаляются на выходе, в том числе при ошибке.

Фотографий в архиве меньше, чем в базе — отказ: у этих анкет картинки не
откроются. Больше — предупреждение: снимок базы делается раньше архива, лишний
файл безвреден.

> В архиве **нет файлов `.webp`** и быть не должно. MinIO хранит объект
> каталогом с именем объекта, а байты кладёт внутрь — в `xl.meta` для мелких,
> в `part.N` для крупных. Искать `*.webp` бесполезно, `backup-check` считает
> каталоги.

### Восстановить

```bash
make restore DUMP=backups/noova-<stamp>.sql.gz
make restore-media ARCHIVE=noova-media-<stamp>.tar.gz
```

Обе разрушительные, требуют `yes`. Восстановление фото останавливает `minio`
на время распаковки.

> Дампы содержат особую категорию по GDPR. `backups/` не в git, копии
> шифруются до того, как покидают машину.

### Чего в копии нет

| | Последствие |
|---|---|
| Redis | сессии — после восстановления все разлогинены; очередь писем `mail:queue` теряется |
| TLS-сертификаты | Caddy выпустит заново |
| DKIM-ключ | живёт на релее, переносится отдельно ([mail.md](mail.md)) |
| `.env` | хранить рядом с копией: без `IP_HASH_SALT` журналы теряют историю |

### Если что-то не так

| Симптом | Причина |
|---|---|
| `не отвечает …(или ключ не принят)` на хранилище | не выполнен `make backup-allow-pull`, либо на проде сменился ключ хоста — тогда удалить строку из `~/.ssh/known_hosts` на хранилище и запустить `backup-storage` заново |
| `самой свежей копии N ч` | снимки на проде не делаются: смотреть `~/noova-snapshot.log` на проде |
| `pull-guard: разрешены только list и fetch` | ключ хранилища используют для чего-то ещё — так и задумано |
| `Дамп оборван: нет завершающей строки pg_dump` | `pg_dump` упал на середине передачи |
| `снимок базы не удался` | сервер недоступен, ключ не принят (`make backup-allow-pull`) или на сервере нет `stream.sh` (`make deploy-files`) |
| `Фотографий в архиве меньше, чем строк в базе` | часть файлов потерялась в MinIO: у этих анкет картинки не откроются. Копия непригодна |
| `Дамп не расшифровался. Тот ли ключ?` | на хранилище лежит закрытая часть не от той пары, которой шифрует прод |

Каталог `backups/` на сервере больше не используется: если он остался от
прежней схемы, его можно удалить вместе с содержимым — это старые
незашифрованные дампы, которым на боевой машине не место.
