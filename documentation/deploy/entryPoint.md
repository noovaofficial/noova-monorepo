## 1. База

```bash
docker compose exec postgres psql -U noova -d noova -c '\dt'
docker compose exec postgres psql -U noova -d noova -c \
  "select relname, n_live_tup from pg_stat_user_tables order by n_live_tup desc;"
docker compose exec -it postgres psql -U noova -d noova
```

`\dt` — таблицы, `\d "Profile"` — колонки, `\q` — выход.

Prisma Studio — **только через SSH-туннель**, порт наружу не открывать:

```bash
ssh -L 5555:localhost:5555 deploy@<IP>
docker compose exec api npx prisma studio --port 5555   # на сервере
```

Дальше `http://localhost:5555` у себя.

> Открытый наружу порт Postgres или Studio — прямой доступ ко всей базе
> с особой категорией персональных данных.

## 2. Бэкапы

Контейнер `backup` делает `pg_dump` по расписанию в `./backups/`
(`BACKUP_INTERVAL_SECONDS`, ротация `BACKUP_KEEP_DAYS`). Этого мало: дамп на
том же диске не спасает от потери сервера.

### Разовая подготовка

```bash
./infra/backup/make-key.sh ~/noova-backup            # у себя
scp ~/noova-backup/backup-public.pem deploy@<IP>:noova/
```

Закрытый ключ остаётся у вас — на сервере ему делать нечего.

### Снять и забрать

```bash
make backup-fetch SERVER=deploy@<IP> DIR=~/noova-backup
```

Дамп базы → архив фотографий → шифрование → скачивание. Порядок важен:
снимок между базой и фото добавит файл без строки (безвредно), обратный
порядок дал бы строку без файла.

### Ежедневный вывоз на вторую машину

Снимок делает крон на проде, а забирает его **хранилище само** — по ssh, ключом,
которому на проде разрешены ровно две команды: список копий и выдача файла.

Направление принципиально. Если бы копии отправлял прод, ключ с правом записи в
архив лежал бы на проде — и тот, кто получил прод, стёр бы вместе с ним и архив,
то есть ровно то, ради чего копии и вывозят наружу.

Порядок (сначала `make deploy-files`, чтобы скрипты были на сервере):

```bash
make backup-cron SERVER=deploy@<IP прода>                    # снимок в 03:20
make backup-storage STORAGE=<user>@<IP хранилища> SERVER=deploy@<IP прода>
make backup-allow-pull SERVER=deploy@<IP прода> KEY='ssh-ed25519 … noova-pull'
```

Второй шаг печатает открытый ключ хранилища и отпечаток ключа прода. Отпечаток
сверьте с тем, что показывает на самом проде `ssh-keygen -lf
/etc/ssh/ssh_host_ed25519_key.pub`: это единственный момент, когда подмену вообще
можно заметить. Третий шаг принимает напечатанный ключ как есть.

Не дожидаясь ночи:

```bash
ssh <user>@<IP хранилища> 'bash ~/pull.sh'    # забрать прямо сейчас
make backup-storage-check STORAGE=<user>@<IP хранилища>
```

| Где | Что | Сколько живёт |
|---|---|---|
| прод, `backups/*.sql.gz` | дампы контейнера `backup`, незашифрованные | `BACKUP_KEEP_DAYS`, 14 |
| прод, `backups/*.enc` | ночные снимки: база + фотографии | `SNAPSHOT_KEEP_DAYS`, 3 |
| хранилище, `~/backups` | те же снимки | `PULL_KEEP_DAYS`, 30 |

Три дня на проде — это три попытки забрать снимок, если ночью хранилище было
недоступно. При работающем вывозе `BACKUP_KEEP_DAYS` разумно снизить до 3:
незашифрованные дампы на боевом диске нужны только для быстрого отката.

Молчание не означает, что всё хорошо. `pull.sh` завершается ошибкой, если копий
нет или самая свежая старше `PULL_MIN_FRESH_HOURS` (26 ч), и пишет в
`~/noova-pull.log`. Чтобы узнавать об этом, не заходя на машину, задайте в
`~/noova-pull.env` переменную `PULL_PING_URL` (healthchecks.io и подобные): пинг
уходит только при успехе, поэтому тревогу поднимает сама тишина.

> Закрытого ключа шифрования на хранилище нет и быть не должно — оно умеет
> только принимать и хранить. Поэтому `make backup-check` по-прежнему
> запускается у вас, на скачанной оттуда копии.

### Проверить

```bash
make infra-up                       # нужен стенд: дамп разворачивается в него
make backup-check                   # свежая копия в ~/noova-backup
make backup-check STAMP=20260829T145907Z
```

Расшифровывает пару, разворачивает дамп в **отдельную** базу, считает объекты
в архиве и сверяет их с числом строк в `Photo`. Расшифрованные файлы живут во
временном каталоге и удаляются на выходе, в том числе при ошибке.

Фотографий в архиве меньше, чем в базе — отказ: у этих анкет картинки не
откроются. Больше — предупреждение: снимок базы делается раньше архива, лишний
файл безвреден.

> В архиве **нет файлов `.webp`** и быть не должно. MinIO хранит объект
> каталогом с именем объекта, а байты кладёт внутрь — в `xl.meta` для мелких,
> в `part.N` для крупных. Искать `*.webp` бесполезно, `backup-check` считает
> каталоги.

### Восстановить

```bash
make restore DUMP=backups/noova-<stamp>.sql.gz
make restore-media ARCHIVE=noova-media-<stamp>.tar.gz
```

Обе разрушительные, требуют `yes`. Восстановление фото останавливает `minio`
на время распаковки.

> Дампы содержат особую категорию по GDPR. `backups/` не в git, копии
> шифруются до того, как покидают машину.

### Чего в копии нет

| | Последствие |
|---|---|
| Redis | сессии — после восстановления все разлогинены; очередь писем `mail:queue` теряется |
| TLS-сертификаты | Caddy выпустит заново |
| DKIM-ключ | живёт на релее, переносится отдельно ([mail.md](mail.md)) |
| `.env` | хранить рядом с копией: без `IP_HASH_SALT` журналы теряют историю |

### Если что-то не так

| Симптом | Причина |
|---|---|
| `can't create /backups/…: nonexistent directory` | каталог `backups/` пересоздали при живом контейнере, bind-mount смотрит на удалённый inode. `docker compose up -d --force-recreate backup` |
| `Permission denied` при шифровании | каталог принадлежит root (его создал контейнер). `sudo chown -R $USER:$USER ~/noova/backups` |
| скрипт молча закончился после дампа | старая версия `snapshot.sh` без `</dev/null` у `exec -T` |
| `не отвечает …(или ключ не принят)` на хранилище | не выполнен `make backup-allow-pull`, либо на проде сменился ключ хоста — тогда удалить строку из `~/.ssh/known_hosts` на хранилище и запустить `backup-storage` заново |
| `самой свежей копии N ч` | снимки на проде не делаются: смотреть `~/noova-snapshot.log` на проде |
| `pull-guard: разрешены только list и fetch` | ключ хранилища используют для чего-то ещё — так и задумано |

Содержимое `backups/` удалять можно, сам каталог — нет, пока контейнер
работает.
