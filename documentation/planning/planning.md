# Noova — роадмап и постановки задач

Единый источник правды по тому, что делается дальше. Объединяет чеклист из
README и новый продуктовый список. Формат рассчитан на то, что задачу берёт
AI-агент с холодного старта: у каждой задачи есть контекст, изменения схемы,
контракты, эндпоинты, краевые случаи и проверяемые критерии приёмки.

Связанные документы: [architecture.md](../arch/architecture.md) — продуктовый контекст
и дизайн-система, [implementation-notes.md](../arch/implementation-notes.md) — неочевидные
технические решения, [README](../../README.md) — запуск и деплой.

---

## 0. Термины и роли

В продуктовых обсуждениях звучит «девушка» и «клиент». В коде таких сущностей
нет и заводить их не нужно — каталог содержит не только индивидуальные анкеты,
но и массажные салоны (`ListingKind.massage`), которые под «девушку» не
подходят. Соответствие такое:

| В обсуждении | В коде | Что это |
|---|---|---|
| «девушка», салон | `User.role = advertiser` + `Profile` | владелец анкеты; одна учётка может владеть несколькими анкетами |
| «клиент» | `User.role = client` *(добавляется в N-02)* | посетитель: избранное, комментарии, просмотр контактов |
| модератор | `User.role = moderator` | проверяет фото, верификацию, комментарии |
| админ | `User.role = admin` | всё вышеперечисленное + управление промо |

**Не заводить отдельную роль под «девушку».** Различие «индивидуальная анкета
или салон» уже выражено полем `Profile.kind` и относится к анкете, а не к
учётной записи.

## 1. Соглашения для исполнителя

Обязательны к соблюдению во всех задачах ниже.

**Контракты идут первыми.** Любое новое поле или эндпоинт начинается с zod-схемы
в `packages/shared/src/`. Оттуда типы забирают и API (валидация запроса и
сериализация ответа через `fastify-type-provider-zod`), и фронт (`apps/web/src/lib/api.ts`
валидирует ответ той же схемой). Рассинхрон должен падать на типах, а не в проде.

**Миграции.** Только `pnpm db:migrate` (`prisma migrate dev`). Уже применённые
файлы миграций не редактировать — накатывать новую. В `docker-compose.yml`
миграции гоняет отдельный одноразовый сервис `migrate`, не сам `api`.

**Приватность по умолчанию.** Публичное API отдаёт только `status = published`.
Персональные данные (email, контакты, документы верификации) не попадают ни в
листинги, ни в SSR-разметку, ни в JSON-LD, ни в логи. `pino` уже вырезает
`authorization`, `cookie`, `password*` — при добавлении новых чувствительных
полей расширять `redact` в `apps/api/src/logger.ts`.

**Локализация.** Ни одной строки в разметке. Все три словаря (`de`, `en`, `ru`)
пополняются одновременно; немецкий — основной рынок, его формулировки главные.

**Стили.** Только CSS Modules и переменные из `apps/web/src/styles/tokens.css`.
Никаких хардкоженых цветов и размеров: тема переключается атрибутом `data-theme`,
и захардкоженное значение сломает светлую тему.

**Проверка перед сдачей.** `pnpm typecheck && pnpm lint && pnpm build` — все три
зелёные. Сборка фронта обязана проходить **при выключенном API** (в Docker бэкенда
на этапе сборки нет): новые серверные запросы на пререндеренных страницах
оборачивать в `safely()` из `apps/web/src/lib/api.ts`.

**Окружение.** Node 22 LTS (`nvm use`). Prisma 7 не работает на Node 23.

**Не ломать без нужды.** Решения из [implementation-notes.md](../arch/implementation-notes.md)
приняты осознанно и с обоснованием. Прежде чем «починить» что-то оттуда —
прочитать, почему так сделано.

### N-29 · Бэкап фотографий и выгрузка наружу

**Зачем.** Сейчас по расписанию снимается только дамп Postgres. Том
`minio_data` не бэкапится вообще: восстановление из дампа даст анкеты,
которые ссылаются на несуществующие фотографии. Половина каталога — это
изображения, и без них восстановленная база бесполезна.

**Зависит от:** —

**Что делать.**
- Второй артефакт рядом с дампом: архив содержимого бакета (`mc mirror`
  или `rclone` в контейнере `backup`).
- Согласованность по времени: снимок бакета и дамп должны относиться к
  одному моменту, иначе в базе есть строка без файла или наоборот.
  Достаточно снимать бакет **после** дампа: лишний файл безвреден,
  отсутствующий — нет.
- Шифрование на стороне сервера (age или gpg) до выгрузки: дампы содержат
  особую категорию по ст. 9 GDPR, и незашифрованная копия у стороннего
  провайдера — это утечка.
- Выгрузка на второй адрес: одна машина — одна точка отказа. Основной риск
  не DDoS (он делает сайт недоступным, но данные не стирает), а
  приостановка провайдером, отказ диска или ошибка оператора.

**Ограничения.**
- **Ключ шифрования не хранится на том же сервере.** Иначе шифрование
  защищает ровно от того, что и так не случится.
- **Восстановление проверяется, а не предполагается.** Непроверенный бэкап —
  это не бэкап; в `make` должна быть команда, поднимающая копию из архива.

**Критерии приёмки.**
- [ ] Фотографии попадают в резервную копию вместе с базой.
- [ ] Копия зашифрована до выхода за пределы машины.
- [ ] Есть команда скачивания последней копии одной строкой.
- [ ] Есть проверенная процедура восстановления из копии.

### N-30 · Пейвол: публикация только после оплаты

**Зачем.** Цены объявлены на `/advertising` (N-28), но платить негде,
и анкета публикуется бесплатно.

**Зависит от:** N-28

**Вопросы к владельцу продукта — нужны до реализации.**
1. **Кто принимает платежи?** Обычные процессоры отказывают взрослому
   контенту. В `architecture.md` §6 намечены CCBill / Verotel / SegPay
   и крипто-фолбэк — нужно подтвердить выбор: от него зависит вся
   интеграция, вебхуки и возвраты.
2. **Что происходит при неоплате?** Анкета снимается сразу, или есть
   льготный период? Снятие в день окончания оплаты — потеря заработка
   из-за задержки банка; бессрочная отсрочка — бесплатное размещение.
3. **Что с уже опубликованными анкетами при запуске пейвола?** Переводить
   их на оплату сразу или дать переходный срок?
4. **Возвраты.** При блокировке анкеты модератором деньги возвращаются?
   Ответ определяет, можно ли вообще блокировать без спора.

**Ограничения, которые видны уже сейчас.**
- **Состояние оплаты — не поле в анкете, а отдельная сущность** с историей:
  «оплачено до» без записей о платежах не даёт разобрать спор.
- **Проверка оплаты на сервере, в маршруте публикации.** Скрытая кнопка
  защищает только от случайного нажатия.
- **Оплата не отменяет модерацию.** Деньги не должны быть способом обойти
  проверку — иначе бейдж «Проверено» теряет смысл.
- **Вебхук идемпотентен.** Процессоры повторяют доставку, и второй вызов
  не должен продлевать срок дважды.
- **Цену нельзя брать из запроса.** Только из справочника тарифов на
  сервере.

### N-31 · Салоны и агентства как разные сущности

**Зачем.** Сейчас `advertiserKind` различает индивидуалку и салон, но
агентство в прайсе есть (N-28), а в системе его нет. Салон и агентство —
разные вещи, и смешивать их нельзя.

**Зависит от:** N-30

**Вопросы к владельцу продукта.**
1. **Чем агентство отличается от салона по существу?** Салон — это место
   с адресом, где принимают; агентство — посредник, ведущий анкеты
   нескольких девушек, возможно без общего адреса. Нужно продуктовое
   определение, а не только цена.
2. **Показывать ли посетителю, что анкета от агентства?** Это влияет
   на доверие и на то, как площадка выглядит с точки зрения L-04.
3. **Общая страница салона/агентства** с перечнем анкет — нужна?

**Ограничение, которое важнее остальных.** Агентство как сущность —
это прямой вопрос к позиции «само-размещение, а не посредничество»
(L-04, L-07 в `legal.md`). Чем более явно система моделирует агентство,
тем труднее утверждать, что анкеты размещают сами девушки. **Юридическую
оценку нужно получить до реализации, а не после**: переделывать модель
данных задним числом дороже, чем отложить.

### N-21 · Продвижение: как анкета попадает в ТОП

**Зачем.** Флаг `Profile.isFeatured` есть в схеме, влияет на выдачу и на
главную — но выставить его сейчас не может никто. Он проставляется
единственным местом в коде: демо-сидом (`i % 5 === 0`). Ни у админа, ни у
модератора, ни у владелицы такой возможности нет, оплаты нет, срока нет.
На чистой базе ссылка «ТОП» в шапке ведёт на пустую страницу, а сортировка
«по релевантности» вырождается в «по свежести».

**Что уже завязано на флаг** (менять придётся с оглядкой на всё сразу):
- сортировка `relevance` — `isFeatured desc` первым ключом;
- блок «Анкеты рядом» на странице анкеты;
- промо-слайдер на главной строится из анкет с флагом;
- фильтр `featuredOnly` в контракте и ссылка «ТОП» в шапке.

**Вопросы к владельцу продукта — на них нужен ответ до реализации.**
1. **ТОП покупается или назначается?** От этого зависит всё остальное: платное
   размещение — это биллинг, счета и возврат средств; назначение вручную —
   это одна кнопка у админа. Промежуточный вариант — назначение вручную
   сейчас и биллинг потом, но тогда флаг с самого начала должен иметь срок.
2. **Есть ли у ТОП срок?** Флаг без срока не снимается никогда: сегодня
   оплаченная неделя, через год — вечное преимущество. Нужен `featuredUntil`,
   а не булев флаг, и фоновая задача, гасящая просроченное (N-18).
3. **Сколько мест в ТОП?** Если флаг может получить каждый, ТОП перестаёт
   что-либо значить: при 100% продвинутых анкет сортировка снова вырождается
   в «по свежести». Нужен либо потолок по городу, либо ротация.
4. **Как ТОП соотносится с верификацией?** Продвигать непроверенную анкету
   значит ставить деньги выше проверки — для каталога 18+ это прямой риск.
   Предлагаемое умолчание: продвижение доступно только верифицированным.

**Ограничения, которые видны уже сейчас.**
- **Булев флаг заменить на срок.** `isFeatured: boolean` не переживёт ни
  одного из ответов выше: и покупка, и ручное назначение требуют «до какого
  числа». Миграция с сохранением данных, как в N-11.
- **ТОП не должен ломать индексацию.** `?featuredOnly=true` — это фильтр,
  а страницы с фильтрами отдают `noindex, follow` (решение из N-12). Если
  «ТОП» задуман как посадочная страница, ей нужен собственный адрес и
  собственный canonical, а не параметр запроса.
- **Порядок внутри ТОП должен быть определён.** Сейчас это `publishedAt desc`,
  то есть продвинутая анкета медленно опускается вниз просто со временем.
  Оплатившие одинаково должны получать одинаковое — иначе это ротация,
  и её нужно проектировать явно.
- **Фильтра «только ТОП» в панели нет.** Переключатели там — `onlineOnly`
  и `verifiedOnly`; `featuredOnly` доступен только ссылкой из шапки. Добавлять
  его в панель имеет смысл после ответа на вопрос 3: фильтр, отбирающий
  большинство анкет, бесполезен.

**Критерии приёмки.**
- [ ] Продвижение выставляется через интерфейс, а не правкой БД.
- [ ] У продвижения есть срок, и просроченное гаснет само.
- [ ] Снятие продвижения сразу видно в выдаче (сброс кэша по тегу).
- [ ] Журнал: кто и когда продвинул анкету и до какого числа.

### N-32 · Страны, города и районы из админки

**Зачем.** Каталог живёт в одном городе — Берлине. Сейчас добавить город
может только разработчик: правка `apps/api/prisma/locations.ts`, выпуск,
скрипт. Сущности `Country` нет вообще, есть поле `City.countryCode`.

**Зависит от:** N-35 — сделана.

**Решения владельца продукта (получены).**
- **Страну заводит главный администратор, не модератор.** Разделение ролей
  в проекте уже есть — новая роль не нужна, нужна проверка `admin` на
  маршрутах.
- **Страна добавляется только после урегулирования правовых вопросов.**
  Это не техническое ограничение, и проверить его кодом нельзя. Форма
  заведения страны должна прямо об этом напоминать — см. ниже.
- **Города и районы переводятся** так же, как услуги. «Berlin» одинаков на
  трёх языках, «München» и «Мюнхен» — нет.
- **Районы опциональны.** Не у каждого города они осмысленны.

**Что входит.**

Часть A — данные и админка. **Сделано:**
- `Country` как сущность с переводами; `City.countryCode` заменён связью
  (миграция `20260824170000_countries`, с переносом существующих данных).
- `isActive` у страны, города и района — отключение вместо удаления.
- Админские эндпоинты `/admin/countries`, `/admin/cities`,
  `/admin/cities/:id/districts`, `/admin/districts/:id` — только роль `admin`.
- Раздел «География» на `/admin`: формы на три языка, районы отдельным
  блоком, отключение переключателем.
- `RESERVED_CITY_SLUGS` и тест, сверяющий список с маршрутами `[locale]`.

Часть Б — маршрутизация. **Сделано:**
- Городской префикс `/{locale}/{city}/...` — главная, каталог, карта.
  Неизвестный или отключённый город даёт 404.
- Переключатель города в шапке: сохраняет страницу, скрыт там, где города
  в адресе нет, и при единственном городе.
- `sitemap.ts`: витринные страницы умножены на города, «Компания» и выбор
  города — без префикса.
- Постоянные (308) редиректы со старых адресов каталога.
- `/{locale}` без города: один город — редирект на него, несколько —
  страница выбора. Отдельного поля «город по умолчанию» не потребовалось.
- Автонакат справочников из `scripts/deploy.sh` **остаётся**: решение
  владельца. Вместо снятия — обратное направление, выгрузка
  `db:export:reference`: справочник правится в админке, возвращается в
  репозиторий файлом и восстанавливается на чистой машине с теми же id.
  **Сделано.**

**Ограничения.**
- **Опциональные районы уже поддержаны, ломать не нужно.**
  `Profile.districtId` — nullable, а `centerFor()` в
  `apps/api/src/modules/account/routes.ts` падает на центр города. Анкета в
  городе без районов получит координату центра города: грубее, а значит
  **приватнее**, что согласуется с `arch/architecture.md` §6, а не спорит
  с ним.
- **Города и районы не удаляются, а отключаются.** На них ссылаются анкеты.
  То же правило, что у услуг.
- **Смена страны у города** — это смена правового режима для всех её
  анкет. Либо запрещать, либо требовать отдельного подтверждения.
- **Правовое поле у каждой страны своё.** Германия не образец для соседей
  (L-09 в `legal.md`). Кнопка «добавить страну» делает шаг лёгким
  технически, но не юридически: **в форме нужен явный чек-лист-напоминание**,
  что правовые вопросы по этой юрисдикции закрыты. Это единственная защита,
  которую здесь можно построить.

**Структура URL — решение принято: префикс в пути плюс переключатель
в шапке.** Поддомены отклонены. Город становится вторым сегментом, после
языка: `/{locale}/{city}/...`.

Это самая дорогая часть задачи, и не из-за самой маршрутизации.

- **Городской префикс получают не все страницы.** Из 19 маршрутов
  привязаны к городу три: главная, `catalog/[kind]` и `catalog/[kind]/map`.
  Анкета — нет (см. ниже). Кабинет, вход, регистрация, админка, модерация и
  страницы «Компания» тоже вне города. Переключатель в шапке должен вести
  себя разумно на обеих группах: на городской странице — оставаться на ней,
  сменив город, на негородской — не ломать навигацию.
- **Слуг города конфликтует с именами маршрутов.** `/ru/about` и
  `/ru/berlin` — оба один сегмент после языка. Next разрешает это в пользу
  статического маршрута, но следствие обязано попасть в форму заведения
  города: **список зарезервированных слугов** (`about`, `advertising`,
  `contact`, `login`, `register`, `account`, `admin`, `moderation`,
  `catalog`, `profile`, `reset-password`, `verify-email`). Город с таким
  именем молча станет недоступен.
- **`Link` придётся оборачивать второй раз.** Сейчас языковой префикс
  подставляет обёртка next-intl (`shared/i18n/navigation.ts`), её импортируют
  32 файла, 42 тега. Город — второе измерение: либо своя обёртка поверх,
  либо город передаётся явно в каждом месте. Первое дешевле и не забывается.
- **Главная без города.** `/ru` должна на что-то указывать: либо редирект
  на город по умолчанию, либо страница выбора города. Пока город один,
  правило всё равно нужно задать явно — иначе оно сложится само и случайно.
- **`sitemap.ts` и hreflang умножаются на города.** Сейчас карта строится
  как «локали × статические пути»; станет «локали × города × пути», и для
  негородских страниц — по-прежнему без города. Ошибка здесь не видна
  глазами: она проявляется просадкой выдачи через недели.
- **Старые адреса нужно сохранить редиректами.** `/ru/catalog/escort` →
  `/ru/berlin/catalog/escort`, постоянным 301. Сайт молодой, но ссылки уже
  существуют.

**Адрес анкеты — без города: `/{locale}/profile/{slug}`.** Решение владельца
продукта.

Что это даёт: **одна анкета — один канонический адрес**. Город в пути
означал бы, что одну и ту же анкету можно открыть из разных городских
контекстов, и за каноничностью пришлось бы следить руками; смена города у
анкеты становилась бы обязанностью вечно редиректить прежний адрес. Здесь
этой обязанности нет вовсе.

Чем платим и чем это компенсировать:

- **В адресе анкеты нет названия города**, а запрос в этой нише почти
  всегда с городом. Компенсируется тем, что и так делается на странице:
  город в `<title>`, в заголовке и в JSON-LD. Разметку хлебных крошек с
  городом стоит добавить в этой же задаче — она даёт городу видимость в
  выдаче без городского сегмента в URL.
- **Переключатель города на странице анкеты.** Страница негородская, менять
  на ней город бессмысленно. Нужно правило: либо переключатель уводит в
  каталог выбранного города, либо на анкете он скрыт. Второе честнее —
  переключатель, молча меняющий страницу, дезориентирует.
- **Ссылки «анкеты рядом» и возврат в каталог** должны нести город явно:
  со страницы анкеты его больше неоткуда взять, кроме данных самой анкеты.

### N-36 · Каталог услуг из админки

**Зачем.** Состав услуг задан в `apps/api/prisma/services.ts` и утверждается
владельцем продукта, но менять его может только разработчик: строка в файл,
ключ в три словаря, прогон скрипта.

**Зависит от:** N-35 — сделана.

**Что входит.**
- Раздел админки: услуги и их группы, создание, изменение, порядок.
- Форма с переводами на три языка — обязательными, как в N-35.
- Признак `appliesTo`: услуга для escort, massage или обеих веток.

**Ограничения.**
- **Услуга не удаляется, а деактивируется.** Она может быть выбрана в
  анкетах, и удаление порвало бы связи. Правило уже реализовано в
  `seed-reference` — админка должна его повторить, а не обойти.
- **Порядок в группе — часть данных, а не оформления.** Поле `position`
  задаёт вид панели фильтров и формы редактирования анкеты; менять его
  нужно из админки, а не пересборкой.
- **Доступ — только `admin`.** Состав каталога определяет, что вообще можно
  предлагать на площадке; для модератора это слишком широкое полномочие.

### N-33 · Агентства: заведение и изменение

**Зачем.** N-31 отвечает на вопрос «что такое агентство» — эта задача о том,
как оно появляется в системе и кто им управляет. Без неё модель агентства
останется схемой, которую некому наполнить.

**Зависит от:** N-31

**Что входит.**
- Заведение агентства: кто создаёт — администратор или сам представитель
  агентства при регистрации.
- Изменение своих данных: название, контакты, описание.
- Привязка анкет к агентству и отвязка. Отдельный вопрос — что происходит
  с анкетой, когда агентство её отпускает или блокируется.

**Вопросы к владельцу продукта.**
1. **Может ли агентство редактировать анкеты своих девушек?** Это граница
   между «ведёт анкеты» и «размещает за них» — и она же граница L-04.
2. **Что видит агентство в кабинете?** Список своих анкет и статистика —
   или полноценная модерация внутри своего пула?
3. **Блокировка агентства** снимает с публикации все его анкеты сразу
   или каждую отдельно?

**Ограничение, которое важнее остальных.** То же, что у N-31: чем полнее
система моделирует управление чужими анкетами, тем труднее утверждать, что
анкеты размещают сами девушки (L-04, L-07). **Юридическая оценка — до
реализации.** Переделывать модель данных задним числом дороже, чем отложить.

### N-34 · Массажные салоны

**Зачем.** Ветка каталога `massage` существует и работает, но салон как
заведение в системе не представлен: `AdvertiserKind.salon` — это признак
рекламодателя, а не сущность с адресом, часами работы и перечнем анкет.

**Зависит от:** N-31

**Что входит.**
- Салон как сущность: название, адрес, часы работы, описание, фотографии
  помещения.
- Страница салона с перечнем анкет — по образцу того, что обсуждается
  в N-31 для агентств.
- Привязка анкеты к салону.

**Вопросы к владельцу продукта.**
1. **Чем страница салона отличается от страницы агентства?** Если ничем,
   кроме адреса, это одна сущность с признаком, а не две.
2. **Адрес салона публичный?** У анкеты координаты намеренно приблизительные
   (район, а не точка). Салон — заведение, а не человек, и точный адрес для
   него нормален, но это осознанное исключение из правила, а не недосмотр.
3. **Часы работы влияют на выдачу?** Например, фильтр «открыто сейчас».

**Ограничения.**
- **Точный адрес салона не должен протекать в анкеты.** Если анкета
  привязана к салону с точным адресом, местоположение девушки перестаёт
  быть приблизительным — а это прямое нарушение допущения из
  `arch/architecture.md` §6.
- **Ветка `massage` уже в проде.** Введение сущности не должно ломать
  существующие анкеты: у них салона нет и может не появиться.

## 5. Сквозные правовые требования

Применимы ко всем задачам, отдельными пунктами роадмапа не выносятся.

**Право на удаление и выгрузку.** Пользователь может потребовать удалить учётку
и выгрузить свои данные. Каскады в схеме это в основном покрывают, но
комментарии и журнал раскрытий требуют отдельного решения: обезличивать или
удалять. Заложить при реализации N-02, а не переделывать потом.

**Сроки хранения.** Журнал раскрытий контактов и записи модерации не должны
храниться вечно. Чистка идёт по расписанию — сервис `jobs`, задачи и сроки
перечислены в разделе «Сделано», N-18. Значения задаются переменными
`RETENTION_*`: это обязательства перед регулятором, и менять их нужно уметь
без выката новой версии.

**Данные особой категории.** Помимо расы (см. N-11), к ним относится всё,
что раскрывает сексуальную жизнь или ориентацию, — а значит, вся анкета целиком
в этой зоне. Отсюда исходное ограничение: минимум полей, никаких документов в
основной БД, шифрование бэкапов.

**Ответственность за размещённое.** Комментарии и фото проходят премодерацию не
из перестраховки: площадка отвечает за то, что опубликовала.

> **Открыт заново:** как анкеты агентства попадают в каталог. От ответа зависит,

Все вопросы этого раздела закрыты — принятые решения перенесены в тексты
соответствующих задач. Список сохранён как история: он объясняет, почему задачи
выглядят именно так.

1. ~~**Хранить ли расу/этнос вообще?** (N-11)~~ — **решено:** самодекларируемый
   «тип внешности», не раса. Формулировки перед запуском показать юристу.
2. ~~**Требовать ли вход для показа контактов?** (N-08)~~ — **решено:** без
   входа, лимит 20/час на IP; при недостаточности — капча, а не вход.
3. ~~**Может ли владелец отвечать на комментарии?** (N-10)~~ — **решено:** нет,
   вместо ответа — жалоба модератору.
4. ~~**Есть ли в комментариях оценка (звёзды)?** (N-10)~~ — **решено:** только
   текст, числового рейтинга нет.
5. ~~**Одна учётка — одна анкета или несколько?** (N-04)~~ — **решено:** у
   индивидуалки одна, у салона несколько; типы не смешиваются.
6. ~~**Кто модерирует на старте?** (N-06)~~ — **решено:** сами, минимальная
   очередь; роли и журнал решений закладываются сразу.
7. ~~**Верификация — провайдер или ручная проверка?** (N-07)~~ — **решено:**
   вручную модератором, с жёсткими правилами хранения документов.
8. ~~**Через что отправляем почту?** (N-15)~~ — **решено:** свой SMTP (Postfix)
   в контейнере, с PTR, прогревом IP и присмотром за чёрными списками.
9. **Кто заводит анкеты девушек, верифицированных агентством?** — открыт.
   Вариант «девушка заводит анкету сама, агентство лишь подтверждает её
   личность» сохраняет само-размещение. Вариант «агентство размещает анкеты
   за девушек» — это посредничество, и именно от него architecture.md §6
   уводит, чтобы не требовалась лицензия «Vermittlung». Технически разница
   в одном: чья учётная запись владеет анкетой.

## 7. Технический долг, замеченный по ходу

Не задачи роадмапа, но чинить дешевле сейчас.

- **Прод развёрнут, стек проверен запуском.** Развёртывание на боевом
  сервере вскрыло семь дефектов, каждый из которых ломал что-то молча:
  образы собирались под платформу машины-сборщика (arm64 на x86-сервере —
  `exec format error`); `prisma.config.ts` не попадал в финальный образ, и
  миграции падали на «datasource.url property is required»;
  `NEXT_PUBLIC_MEDIA_URL` не передавался в сборку, из-за чего оптимизатор
  картинок отвергал боевой домен; `ACME_EMAIL` не доходил до Caddy;
  `caddy` и `minio` жили в разных сетях, и `/media` отдавал 502; в пути к
  MinIO не было имени бакета; первого администратора нельзя было создать —
  скрипт требовал `tsx`, которого в прод-образе нет. Всё исправлено и
  проверено на живом сервере. Процедура — в `documentation/deploy/`.

- **`/favicon.ico` отдаёт 500, а не 404.** Прокси пропускает путь без языкового
  префикса в `[locale]/page.tsx` со значением `locale = "favicon.ico"`, и
  `new Intl.NumberFormat(locale)` бросает `RangeError`. Неизвестный путь из
  одного сегмента (`/xx`) редиректится, из двух (`/ru/nope`) даёт честный 404 —
  ломается только первый случай. Чинится проверкой локали в `proxy.ts` либо
  реальным `app/favicon.ico`. Замечено при работе над N-08, к ней отношения
  не имеет.

- **`Profile.tags` больше не используется.** Свободные теги из прототипа
  заменены справочником услуг: набранные руками, они расходились в написании
  («ужин» / «Ужин» / «dinner»), не переводились на три языка и не годились для
  фильтров. Поле осталось в схеме пустым — удалить отдельной миграцией, когда
  станет ясно, что оно точно никому не нужно.
- **Состав каталога услуг — стартовый.** Он задан в
  `apps/api/prisma/services.ts` и переводится ключами `services.*` в словарях.
  Таксономию должен утвердить владелец продукта: добавление услуги — строка
  в файл, ключ в три словаря, `pnpm --filter @noova/api db:seed:reference`.
  Тем же скриптом заводятся города и районы (`prisma/locations.ts`) — то же
  ограничение, та же задача N-32.
- **`Profile.age` хранит возраст числом.** Он протухает: анкета, заведённая с
  «21», через два года всё ещё показывает 21. Правильно хранить год рождения и
  считать возраст на отдаче. Совместить с миграцией в N-11.
- **Весь словарь локали уезжает на клиент** (см. implementation-notes). При
  росте числа строк передавать в `NextIntlClientProvider` только нужные
  неймспейсы.
- **Тестов мало.** Есть 11: обработка изображений (включая вычистку EXIF и
  защиту от «бомб сжатия») и клиент кабинета. Не покрыты построитель фильтров
  (`modules/profiles/query.ts`) и мапперы — там логика, которую легко сломать
  незаметно. Оба места стоит закрыть заодно с N-12.
- **`docker-credential-desktop` вне `PATH`** на машине разработчика — команды
  `docker compose` падают на аутентификации реестра. Чинится в профиле шелла.
- **Dev-сервер фронта упирается в `EMFILE`** после десятка перезапусков:
  файловый наблюдатель накапливает дескрипторы. Страницы отдаются, но горячая
  перезагрузка может пропускать изменения — помогает перезапуск `pnpm dev:web`.
